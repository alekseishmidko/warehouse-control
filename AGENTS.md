# Правила работы агента

## Назначение и навигация

Warehouse Controller — учебная WMS: приёмка, размещение, резервирование, сборка и
отгрузка. Документация и поясняющие комментарии — на русском; код и идентификаторы —
на английском. Цель — поддерживаемая реализация согласованных бизнес-требований.

Перед изменением прочитать:

1. [Карту и статус](docs/README.md), текущую задачу [плана](docs/development-plan.md).
2. [Архитектуру](docs/architecture.md), [домен](docs/domain.md), принятые [ADR](docs/adr/README.md).
3. [Контракты](docs/contracts/README.md), README затронутых модулей и владельца flow.
4. [Стандарт документации](docs/documentation-standard.md), [shared](docs/shared.md).
5. [Правила качества](docs/quality.md), [ревью](docs/code-review.md), [проверки PR](docs/pr-checks.md).

Здесь хранятся действующие правила работы. История реализации — в docs/reports;
фактический статус — в docs/README и плане. Не копировать историю WMS-этапов обратно.
Не считать описание или согласование доказательством реализации.

## Требования до кода

- Перед реализацией определить вход, доверие к нему, права, предусловия, успешный
  результат, ошибки, инварианты и границы задачи. Использовать [шаблон изменения](docs/templates/change.md).
- Критерии приёмки имеют стабильные ID. Связывать каждый критерий с реализацией и
  проверяющим тестом. Непроверенное отмечать явно, не объявлять готовым.
- Новое бизнес-решение не угадывать. Выполнить независимую работу и согласовать
  решение до зависимой реализации. Технические детали в согласованном объёме выбирать самостоятельно.
- При изменении требований сверить действующие код/тесты/контракты. Сохранить различие
  между принятым правилом и ещё не выполненной реализацией.
- Менять только нужное для задачи. Не выполнять весь roadmap за один шаг.
  Архитектурное изменение оформить ADR со ссылкой на заменяемое решение.
- Разрешение менять репозиторий не означает разрешение публиковать или разворачивать его извне.

## Архитектура и читаемость

- Frontend WMS-208 реализован в apps/web: Solid/TypeScript/Vite SPA, Solid Router,
  @tanstack/solid-query, Tailwind, ADR-0026/0027. Версии и запуск — apps/web/README.md.
  Не добавлять React runtime или backend imports. Бизнес-правила остаются на сервере.
  После неизвестного результата сохранять исходную команду/key; replay только явно.
  Query cache разделяется по user/warehouse/filters и очищается при logout/401.

- Модульный монолит; API и worker — разные процессы одного backend. Сначала PostgreSQL
  transactional outbox, затем Kafka с сохранением outbox. Не добавлять Redis/BullMQ,
  микросервисы или Event Sourcing без нового ADR.
- По умолчанию controller → service → private repository. Services, repositories, DTO
  лежат в services/, repositories/, dto/, даже при одном файле. Controller отвечает за
  HTTP, service — за сценарий, repository — за SQL. Модули экспортируют сервисы.
- Прямые записи в чужие таблицы запрещены. Не импортировать чужие repositories.
  Чтение полиморфного audit scope через retained связи — исключение ADR-0025.
- Одна функция решает одну понятную задачу. Имя метода объясняет действие/объект;
  точное длинное имя лучше неоднозначного короткого. Не объединять независимые операции
  набором переключающих флагов. Не вводить произвольные лимиты строк функции вместо анализа ответственности.
- Перед новой утилитой искать существующий код через rg. Общая техническая логика —
  shared/<capability>; I/O adapters — infrastructure; общее между приложениями — packages
  только при реальных потребителях. Бизнес-правило остаётся у владельца модуля.
- Shared не зависит от modules/infrastructure. Не создавать utils-свалки, universal
  base service или слои/interfaces/tokens только ради похожего синтаксиса.
- TypeScript strict не ослаблять. Запрещены explicit any, ts-ignore/ts-nocheck и
  необработанные Promise. Narrowing unknown предпочтительнее приведения. Обоснованные
  ts-expect-error/lint exceptions требуют причины; не использовать их ради зелёного gate.

## Транзакции, склад и безопасность

- Только inventory изменяет stock и allocations/reserved. Количество — целые штуки
  int4 0..2147483647, положительная операция 1..MAX; 0 <= reserved <= onHand.
  reserved=SUM(active allocations) для каждого balance, без legacy исключений.
  allocated=active+released+transferred+consumed. Available=onHand-reserved;
  резервировать можно только storage. [Правила](docs/fulfillment-rules.md).
- Бизнес-изменения, movements, audit, outbox и saved HTTP result коммитятся атомарно.
  Владелец сценария открывает TRANSACTION_RUNNER.run; вызываемые сервисы получают
  один opaque TransactionContext. Nested/stale/cross-scope context, fire-and-forget,
  подавление SQL ошибок и внешнее I/O внутри callback запрещены. Auto retry нет.
- Блокировки и режимы выбирать до мутаций, соблюдать стабильный порядок. Проверять
  SHARE→UPDATE upgrades, absent-key races и состояние после ожидания. [Транзакции](docs/transactions.md).
- История immutable, исправления — новые факты. Применённые migrations не редактировать;
  создавать новые с политикой существующих расхождений. DBA может обойти runtime guards.
- Аудит писать через AuditService с безопасными changes и основанием. Ошибка аудита
  откатывает сценарий. Нельзя сохранять секреты, токены или реальные персональные данные.
- Actor/roles задаёт серверная session, не body/headers. Dev actor обхода нет.
  Проверять фактический warehouse ACL в общем context до replay каждой команды.
  System admin без warehouse роли не получает складской доступ.
- Cookie/CSRF/session/bootstrap policy не упрощать ради теста или demo.
  [Владелец identity](docs/identity.md), [locks и HTTP flow](docs/flows/identity.md).

## События, фоновые сценарии и чтение

- Доставка at least once; handler effect/marker/cursors/ack — один commit.
  Не обещать exactly once, глобальный порядок или атомарность БД + Kafka.
  Не заменять durable delivery EventEmitter/fire-and-forget.
- Writer проверяет envelope/payload до INSERT; handler — до эффекта. Source schemas —
  docs/contracts/events; generated output менять только генератором.
  Новый consumer требует migration/replay/start-position плана.
- Lease token защищает от stale worker; dead блокирует свой stream. SIGTERM прекращает
  claim и ограниченно ждёт обработки. [Worker flow](docs/flows/worker.md).
- Recovery CLI только по явному local opt-in и DB admin role; retries сохраняют eventId,
  историю и attempts. [Recovery](docs/flows/outbox-recovery.md).
- Списки требуют склад и read/audit ACL, включая cursor replay. Audit scope определяется
  retained объектом, не JSON changes/correlationId. DTO не выдают ORM или credentials.
- Cursor сохраняет microseconds; не округлять ключ через Date. Limit 1..100/default20.
  Не обещать общий snapshot между страницами. Putaway появляется после commit worker.
  [Чтение](docs/flows/warehouse-reads.md), [outbox](docs/outbox.md).
- B1–B4: partial pick/ship разрешены; нехватка не списывает stock автоматически;
  staged cancel → cancel_pending → полный физический возврат; shipped не отменяется.
  Автоматического expiration/TTL/job для резервов нет.

## Документация

- Каждый backend/shared/infrastructure модуль имеет README по шаблону: бизнес- и
  технический раздел, взаимодействие, шаги данных, ошибки, пример, тесты.
- Собственные source/test/script файлы имеют file-level JSDoc и контракты публичных
  символов. Комментарии объясняют причины проверок, locks, преобразований, повторов
  и commit/rollback. Не пересказывать синтаксис и не дублировать типы без смысла.
- Каждое поле schema описывает назначение, SQL-тип, единицы/диапазон, default/NULL,
  SQL/JS/JSON нюансы; keys/CHECK/indexes — причину. Не править applied/generated ради комментариев.
- Для сценария обновлять подробный flow с Mermaid, доверием к входу, SQL/событиями,
  результатами, ветками отказа и evidence. README ссылается на одного владельца подробностей.
- Новые собственные файлы включать в docs/file-catalog.md. Форматы без комментариев
  объяснять в ближайшем README. Generated имеет источник и команду, output вручную не правится.
- Использовать принципы ASD-STE100, адаптированные к русскому: простые предложения,
  единые термины, явный участник. Не заявлять формальное соответствие английскому словарю.
- Обновлять существующие утверждения, не дописывать противоположный статус в конец.
  Общие правила не копировать между документами; давать ссылку на владельца.

## Тесты, ревью и завершение

- После каждого законченного изменения интерфейса/правил/фичи выполнять ревью без
  отдельного запроса: diff/новые файлы/связанные пути → исправления и regression tests
  → повторное ревью → проверки исправленного функционала. Это относится и к bugfix.
- При отдельном запросе только на review код не менять без поручения исправить.
  Findings оформлять по docs/code-review.md; не придумывать дефекты ради количества.
- Каждый поведенческий дефект закреплять regression test; по возможности показать
  отказ до исправления. Не ослаблять тест или менять ожидание ради успешного прогона.
- После изменения кода, scripts, конфигурации или переменных окружения определить
  затронутые пользовательские команды и выполнить их на итоговом состоянии.
  При исправлении сбоя обязательно повторить исходную команду пользователя через
  тот же entry point, с теми же аргументами и в условиях, вызвавших сбой.
  Unit tests, сборка, config validation, изолированный gate и запуск вложенной команды
  не заменяют эту проверку. Новые обязательные настройки проверить также со старой
  конфигурацией: нельзя объявлять исправление готовым, оставив исходный запуск сломанным.
  Для длительно работающих команд проверить фактическую готовность сервисов и штатную
  остановку; успешное создание процесса не доказывает успешный запуск.
  Соблюдать ограничения на рабочие данные и внешние действия. Если проверка невозможна
  без недостающего доступа, настройки или разрешения, явно указать блокировку и считать
  команду непроверенной. В итоговом отчёте привести точные команды, результаты и ограничения;
  не заявлять успешный запуск без фактического выполнения.
- Тесты проверяют наблюдаемые бизнес-результаты и отсутствие недопустимых эффектов при
  отказе. Для SQL/locks/outbox нужны реальные migrations/PostgreSQL, не только mocks.
  Гонки доказывать barriers/DB waits; освобождение ресурсов — finally.
- Тесты независимы от порядка, общего изменяемого состояния и случайных ожиданий.
  Fixtures вызывают production owners и не копируют бизнес-алгоритмы. Прямой stock SQL
  допустим для проверки constraints; обход retained triggers — только disposable cleanup.
- Покрытие требований и coverage кода — разные измерения. Все критерии должны иметь
  evidence; цель бизнес-веток 100%, фактические пробелы и child-process gaps явно указаны.
  [Политика и команды](docs/quality.md); не объявлять весь backend покрытым на 100%.
- Перед PR выполнить pnpm check:pr на итоговом diff. Он включает формат, typed lint,
  architecture guard/self-tests, typecheck/build/contracts/OpenAPI, unit/integration
  web generation/build/Vitest, Chromium gate и coverage обоих приложений с отдельными
  baseline. Ревью команда не заменяет. Внешний CI не настроен.
- Docker и установленный Playwright Chromium обязательны для integration;
  `pnpm exec playwright install chromium` выполняется до первого прогона.
  Skip/fallback/forceExit запрещены. Не запускать
  несколько test:prepare/check:pr/coverage одновременно в checkout.
  Перед этими командами остановить dev:all/Nest watch: они пишут общий dist.
  Общие helpers проверять на всех потребителях. [Test harness](apps/backend/test/README.md).
- Отчёт: изменения, AC → код → tests, найденные/исправленные замечания, повторное ревью,
  команды/результаты/coverage gaps и ограничения. Не скрывать неисполненные проверки.
  Использовать docs/templates/pull-request.md; статусы поддерживать в docs/README/roadmap.
- Dockerfile/Compose изменены → дополнительно image-check/gate. Не менять рабочую .env,
  dev volumes или внешний deployment ради проверки. [Docker](docs/flows/docker-gate.md).
