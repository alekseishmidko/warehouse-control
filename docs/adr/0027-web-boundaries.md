# ADR-0027. Read справочники и восстановление команд SPA

- Дата: 2026-11-04.
- Статус: Accepted; техническая реализация согласованной WMS-208.
- Дополняет [ADR-0026](0026-solid-frontend.md), [read API](0025-warehouse-reads.md)
  и [HTTP idempotency](0013-http-idempotency.md).

## Контекст

SPA должна выбрать доступный склад, товар и ячейку. Ранее UI не имела этих списков.
После потери ответа клиент не может определить, зафиксировал ли сервер команду.
API не предоставляет отдельный публичный endpoint для поиска результата по ключу.

## Решение

Добавлены три read-only route: GET `/api/v1/warehouses`,
`/api/v1/warehouses/:warehouseId/products` и `/locations`.
DirectoryReadController — API composition, не новый бизнес-модуль. Он проверяет
session/ACL через AccessService, затем вызывает сервис владельца справочника.
Repository остаётся private. Общий ApiReadPage decorator переиспользуется с WMS-207.

Список складов содержит только назначения с действием read; system_admin без
назначения получает пустую страницу. Ячейки ограничены warehouse predicate в SQL.
Каталог общий для единственной организации: products возвращает все товары после
проверки read к выбранному складу. Модель принадлежности товара складу не вводится.
Публичного write CRUD нет. Используются существующие limit 1..100/default20 и keyset
по уникальному UUID ASC. Cursor склада связан с userId и текущим набором grants;
другой набор отклоняет cursor. Остальные cursors связаны с ресурсом и складом.
Новых таблиц, индексов и миграций для этих запросов не требуется: используются PK.

Перед складской mutation клиент сохраняет URL, точный JSON body, correlationId,
idempotency key, userId и warehouseId в sessionStorage. Одна неизвестная команда
блокирует создание следующей для этого пользователя во вкладке. Token/password/CSRF
не сохраняются. Перед отправкой используется актуальная серверная сессия.

Сетевой timeout/5xx сохраняет запись. Человек явно повторяет исходный запрос с тем же
ключом в исходном складе. API снова проверяет права, затем возвращает saved result или
выполняет команду. Первый явный 4xx, кроме 401, завершает новую попытку отказом.
Ошибка replay сохраняет старую запись: ACL/DTO могут отклонить повтор до lookup
сохранённого результата, поэтому новый 403/409 не доказывает rollback первой команды.

## Альтернативы и ограничения

Автоматический повтор с новым ключом создаёт риск второй операции и запрещён.
Автоматический replay с прежним ключом после reload тоже не выбран: ещё не выполненная
команда могла перестать соответствовать намерению человека. UI предупреждает об этом.
Отдельный status endpoint потребовал бы нового контракта доступа/retention и сейчас
не нужен для поддерживаемого POST replay.

sessionStorage переживает reload, но теряется при закрытии вкладки. Между вкладками
нет общей блокировки. Серверные guards сохраняются; новая вкладка может создать новую
намеренную команду. Не обещать глобальную дедупликацию всех кликов по смыслу операции.
Для восстановления после закрытия вкладки нужна отдельная задача на долговременный
журнал/доступ к истории команд. При отозванном доступе запись сохраняется для разбора,
а API не раскрывает прежний saved result. Очистить запись обходом интерфейса — не
доказательство того, что исходная операция не выполнилась.
