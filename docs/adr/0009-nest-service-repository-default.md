# 0009. Controller → service → repository по умолчанию

- Дата: 2026-10-19
- Статус: Accepted
- Supersedes: часть ADR-0008 об отдельном AuditWriter port/adapter; транзакционные гарантии ADR-0008 сохраняются.

## Контекст

Пользователь выбрал обычный NestJS как базовый стиль проекта. Обязательное
application/domain/infrastructure-разделение добавляет переходы и интерфейсы
даже для небольших модулей. Более сложную организацию будем вводить по необходимости.

## Решение

Бизнес-модуль начинается с module, controller при наличии HTTP, service и repository
при наличии DB I/O. Сервис содержит сценарии/правила, repository — SQL/ORM,
controller — HTTP DTO/validation и отображение результата/ошибки.
Межмодульное взаимодействие — через экспортируемые сервисы; repository остаётся
внутренним provider. Нет обязательных interface/token для каждого сервиса и repository.
Не нужны пустые controller или repository, если у модуля нет соответствующей задачи.

Audit переведён на AuditService → AuditRepository. Service проверяет/маскирует
input, repository выполняет INSERT с тем же обязательным TransactionContext.
Отдельные AuditWriter/AUDIT_WRITER/PostgresAuditWriter удалены, schema/helper лежат рядом.
HTTP-контроллер аудита не добавлен, поскольку API истории пока не реализован.

Shared и общая infrastructure остаются. Уже проверенный TransactionRunner/Context
сохраняется как обоснованная общая техническая абстракция для атомарных сценариев
нескольких сервисов. Это не требование строить ports/adapters для каждого модуля.
Миграции, таблицы, redaction, append-only права и отказ от auto retry не меняются.

## Когда отходить от базового подхода

Если сервис стал трудно обозримым — выделить сценарии и чистые функции правил.
Если появились реальные альтернативные реализации/транспортные границы — ввести port.
Если сложные инварианты требуют самостоятельной модели — локально выделить domain.
Причину и границу отклонения описать в README модуля; изменение архитектурных
гарантий/границ зафиксировать новым ADR. Не создавать слои заранее по шаблону.

## Альтернативы

Обязательные слои дают строгую структуру, но избыточны для простых операций.
Один service с SQL сокращает файлы, но смешивает сценарий с хранением; repository
сохраняем там, где есть обращения к БД. Микросервисы не решают задачу организации
текущего кода и не входят в это изменение.

## Последствия и проверка

Меньше вспомогательных контрактов и более привычный Nest DI. Правила зависимостей
и атомарность по-прежнему требуют дисциплины. Проверяем service validation/delegation,
общий PostgreSQL commit/rollback, permissions, Nest DI и отсутствие schema diff.

## Уточнение структуры и документации

Сервисы размещаются в services/, repositories в repositories/, DTO в dto/,
даже если файл один. README содержит схему взаимодействия, пошаговое движение
данных, примеры DTO и ошибки/транзакционные границы. Это организационное уточнение,
не смена подхода или гарантий; детали — в [стандарте документации](../documentation-standard.md).
