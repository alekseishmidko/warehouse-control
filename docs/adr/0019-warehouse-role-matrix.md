# 0019. Роли и матрица доступа к складам

- Дата: 2026-10-29
- Статус: Accepted; runtime checks реализованы WMS-202.
- Основание: ответ владельца продукта «утверждаю матрицу взаимодействия» после
  предложения ролей/складской матрицы WMS-202.1.
- Дополняет [ADR-0018](0018-server-sessions.md): способ auth и модель угроз сохраняются.

## Контекст

Пользователь может работать на нескольких складах с разными полномочиями.
Глобальное объединение «роль где-нибудь» и «доступ к нужному складу» позволило бы
кладовщику склада A изменять склад B, где ему разрешено только чтение.

## Решение

Принята матрица [identity.md](../identity.md#роли-и-складская-матрица): viewer,
warehouse_operator, order_manager, warehouse_supervisor и system_admin.
Таблица в identity.md — единственный владелец подробного соответствия действий ролям;
не копировать её в несколько документов с разными версиями прав.

Четыре складские роли назначаются на конкретный warehouse: `(userId, warehouseId, role)`.
Для команды проверяется подходящая роль на складе самого объекта; списки ограничены
разрешёнными складами. Проверка проводится сервером на каждом запросе и перед HTTP replay.
system_admin управляет пользователями/назначениями и чужими сессиями, но не получает
складские действия автоматически: для них требуется отдельное складское назначение.

Не указанные в таблице действия по умолчанию запрещены. Глобальный catalog, системный
аудит и эксплуатационный outbox retry требуют явных permissions до добавления их API.
PostgreSQL warehouse_outbox_admin не становится ролью пользователя приложения.
Роли приложения не отменяют бизнес-состояния, CSRF, общие транзакции или инварианты inventory.

## Альтернативы

- Одна глобальная роль на пользователя: не выражает разные обязанности на разных складах.
- Неявный полный складской доступ system_admin: не выбран владельцем продукта.
- Отдельный permission engine: сейчас не требуется для принятой фиксированной матрицы.

## Последствия и проверка

WMS-202.1 завершена как согласование способа auth, модели угроз и матрицы. Проверки ACL/guards/назначений реализованы WMS-202.2–202.6;
[фактический отчёт](../reports/wms-202.md). Будущие tests должны
покрыть operator A + viewer B, чужой UUID/списки, запрет неуказанного действия и replay
после отзыва доступа. Согласование не означает уже действующие ограничения в runtime.

Сроки сессий не утверждены этим решением: 12h absolute/30m idle остаются предложением
для WMS-202.2. Истечение сессий не связано с принятым запретом автоматического expiration
товарных резервов. Bootstrap, cookie/CSRF и identity endpoints реализованы WMS-202; внешнего deployment нет.
