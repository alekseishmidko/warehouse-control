# 0023. Сборка из действующего резерва

- Дата: 2026-11-01.
- Статус: Accepted. Владелец продукта утвердил первый вариант назначения исполнителя.
- Уточняет ADR-0022 и реализацию B1–B4; опубликованный OrderChanged v1 сохраняется.

## Решение

Менеджер заказа с правом order создаёт задание из всех текущих storage allocations
активного заказа. Одновременно открыт только один план этого заказа. План содержит
1..1000 строк allocations. Это строки источников, поэтому один SKU может занять несколько
строк. Пустой план отклоняется. Создание не меняет остатки и не увеличивает резерв.

Кладовщик с правом pick сам берёт ready задание командой start. Сервер назначает
исполнителя из Principal. Подтверждает только этот исполнитель с действующим правом pick.
Состояние shortage возобновляет тот же исполнитель через start после проверки товара.
Переназначение и автоматическое возвращение задания в общую очередь не реализованы.

Для однозначного закрепления подтверждение требует in_progress. Обобщённая проектная
таблица WMS-201 допускала ready → подтверждение; в этом API сначала обязателен start.
Это исключает обход выбранного правила назначения. Новая команда не меняет чужое назначение.

Одна confirm-команда содержит одно приращение actualQuantity одной строки. Положительное
количество переносится в shipping своего склада. Ноль разрешён только с shortage=true,
не создаёт движений. shortage=true требует оставшееся количество задания после подтверждения.
Плановые и фактические количества — int4 штуки; HTTP и событие ограничены 262144 UTF-8 bytes.

## История и транзакции

Fulfillment владеет task/lines, inventory — balances, allocations и transfer history.
Исходный allocation сохраняет transferred; allocated=active+released+transferred.
Shipping получает новый allocation, связанный с источником через picking_transfers.
Перенос не является release и не увеличивает открытое количество заказа.

У пары движений сборки отдельный pickingTransferId. transferId размещения остаётся FK
на PutawayTask. Новый CHECK разрешает ровно одно основание пары; старый deferred guard
размещения не снимается. Новые deferred guards сверяют пару, историю allocations,
строку задания и баланс reserved=SUM(active). Таблицы истории retained/immutable.
Это защита от runtime роли, не от администратора БД.

Порядок locks: policy → idempotency → order UPDATE → task UPDATE → balances в порядке
product/location. GET задания берёт order SHARE. Команда фиксирует task, stock/reserve,
movements, audit, outbox и saved response одним commit. Внешнего I/O внутри callback нет.

Пока есть открытый план, независимый release заказа отклоняется, чтобы не обесценить
план. Отмена до первого переноса закрывает task и освобождает storage reserve атомарно.
После переноса отмена отклоняется до физического возврата WMS-206; shipping резерв не
освобождается обычным release. B3 не отменён. Автоматического expiration нет по B4.

## Событие, альтернативы и проверка

PickingProgressed v1 — новый aggregate picking-task с taskId/orderId/action.
Подписчиков пока нет; появление outbox факта не означает внешней доставки.
Расширение enum опубликованного OrderChanged v1 не выбрано.
Перезапись balance_id исходного allocation не выбрана: она скрывает историю источника.
Перенос через release+reserve не выбран: он меняет смысл резерва и допускает захват товара.
