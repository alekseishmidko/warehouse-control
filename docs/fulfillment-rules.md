# Правила заказа, резерва, сборки и отгрузки

Документ описывает действующие бизнес-правила B1–B4 и реализацию WMS-204–206.
Источники технических решений: [ADR-0022](adr/0022-order-reservations.md),
[ADR-0023](adr/0023-picking-execution.md), [ADR-0024](adr/0024-shipment-compensation.md).
Первоначальный проект WMS-201 и прежние промежуточные статусы сохранены в
[историческом архиве](reports/wms-201-rules-archive.md). Архив не задаёт текущий контракт.

Обзор продукта — [product](product.md), складские инварианты — [domain](domain.md).
Подробности HTTP/SQL и проверки находятся у владельцев сценариев:
[reservations](flows/reservations.md), [picking](flows/picking.md),
[shipping](flows/shipping.md). Этот документ определяет бизнес-политику, а flow — её выполнение.

## Принятые решения

B1–B4 приняты владельцем продукта 2026-10-29. Последующие ADR уточняют реализацию.

| ID  | Действующее правило                                                                                                                               |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| B1  | Частичные сборка и отгрузка разрешены. Неисполненный остаток заказа остаётся открытым.                                                            |
| B2  | Оператор фиксирует найденное количество и нехватку. Недособранное остаётся в резерве; автоматического списания stock нет.                         |
| B3  | Отмена закрывает весь неотгруженный остаток. Собранное требует полного подтверждённого физического возврата в storage. Отгруженное не отменяется. |
| B4  | Автоматического истечения резервов нет. Возраст резерва не освобождает товар.                                                                     |

## Область и количества

Заказ принадлежит одному складу. Его 1..1000 строк уникальны по productId. Quantity —
целые штуки: положительная операция 1..2147483647, balance/counters 0..2147483647.
Суммы проверяются без переполнения int4; допустимая отдельная строка не разрешает
переполнить накопленный баланс. На каждом balance:

`0 <= reserved <= onHand`; `available = onHand - reserved`;
`reserved = SUM(active allocations)`.

Резервировать можно только storage. Receiving и shipping не дают свободного товара
для нового заказа. Команда явно задаёт резервируемые количества; нехватка откатывает
весь вектор, молчаливого уменьшения количества нет. Подтверждение заказа само не резервирует.

Для строки заказа:

`ordered = open + reservedStorage + reservedShipping + shipped + cancelled`.

Собранное учитывается только в reservedShipping. Все части неотрицательны. Shipped
и cancelled — накопленные терминальные количества. Исходное ordered не уменьшается
для сокрытия недостачи.

Для каждой сохранённой allocation:

`allocated = active + released + transferred + consumed`.

При сборке исходная allocation увеличивает transferred, а новая shipping allocation
получает active. Это перенос существующего обеспечения, а не второй независимый резерв.
Released/consumed/transferred сохраняют причину закрытия количества; их нельзя стирать
или повторно потреблять. Подробная модель — [domain](domain.md).

## Заказ и явный release

| Состояние      | Команда / условие                             | Результат                                                              |
| -------------- | --------------------------------------------- | ---------------------------------------------------------------------- |
| draft          | Подтвердить                                   | active, состав зафиксирован, stock прежний                             |
| draft          | Отменить                                      | cancelled, резервов нет                                                |
| active         | Reserve / pick / частичный shipment           | active, меняются количества                                            |
| active         | Отгрузить всё ordered                         | completed, активных резервов нет                                       |
| active         | Отменить остаток без shipping allocations     | cancelled при shipped=0, иначе closed_mixed; storage резерв освобождён |
| active         | Отменить остаток с shipping allocations       | cancel_pending; исполнение заморожено, stock и резерв пока сохранены   |
| cancel_pending | Подтвердить полный возврат и закрытие остатка | cancelled при shipped=0, иначе closed_mixed                            |
| cancel_pending | Ошибка возврата                               | cancel_pending; учётный эффект откатан                                 |

Отдельного состояния partially_shipped нет: частично отгруженный открытый заказ остаётся
active. Closed_mixed отличает частичное исполнение с отменой остатка от полной отмены.
Completed/cancelled/closed_mixed терминальны. Нельзя менять состав active, отгружать
cancel_pending, возвращать terminal в active или отменять уже shipped.

Явный release storage разрешён active заказу без открытого плана сборки. Он уменьшает
резерв, но не физический onHand. Отмена заказа сначала закрывает неисполненный план,
затем освобождает остаток. Storage release не заменяет возврат собранного товара.

## Сборка и нехватка

План использует уже существующие storage allocations и сам не создаёт резерв.
В задании не больше 1000 строк. Для строки:

`planned = pickedTotal + cancelledUnpicked + remaining`.

Planned неизменно; pickedTotal остаётся историей даже после последующего возврата.
Ready требует явного start, который закрепляет исполнителя и переводит задание в
in_progress. Подтверждать сборку может закреплённый исполнитель только из in_progress.
Частичная сборка оставляет in_progress, полная завершает задание в completed.

При нехватке найденная часть переносится storage→shipping, задание становится shortage,
а недособранный резерв сохраняется. Actual=0 допустим для сообщения о нехватке при
положительном remaining; нулевого stock movement нет. Возобновление из shortage требует
start прежнего исполнителя. Completed/cancelled нельзя снова собирать.
Команда сверх remaining/active либо ошибка прав/SQL откатывает весь результат.
Нехватка сама не корректирует onHand и не освобождает чужой резерв.

## Отгрузка

Shipment одного заказа/склада содержит 1..1000 уникальных allocationId. Draft не меняет
stock и не создаёт новое обеспечение. Несколько draft могут ссылаться на одну staged
часть; каждый posting заново проверяет фактический active под блокировками.

| Состояние | Команда                                                | Результат                                                          |
| --------- | ------------------------------------------------------ | ------------------------------------------------------------------ |
| draft     | Провести при достаточном shipping active своего заказа | posted; onHand/reserved/active уменьшаются, consumed увеличивается |
| draft     | Отменить документ                                      | cancelled, stock/резерв прежние                                    |
| draft     | Нехватка, запрет состояния или SQL ошибка              | Весь posting откатан, документ остаётся draft                      |
| posted    | Повтор исходного ключа после проверки доступа          | Исходный сохранённый ответ без нового эффекта                      |

Posting атомарен по всем строкам. Частичный shipment — полностью проведённый документ
части заказа. Отгрузка напрямую из storage, чужого allocation или сверх остатка запрещена.
Posted нельзя редактировать/отменять. Возврат от клиента — отдельный будущий процесс.

## Отмена и физический возврат

Отмена произвольной части строки не реализована: отменяется весь неотгруженный остаток.
При staged товаре заказ сначала становится cancel_pending. Оператор физически возвращает
товар в storage своего склада, затем подтверждает полный вектор: 1..1000 уникальных
orderLineId с количеством, равным активному shipping остатку каждой строки.

Fulfillment удерживает order lock. Inventory раскрывает вектор в allocations и заранее
берёт объединение shipping-источников, storage-назначений и всех storage balances
остаточного резерва заказа в общем порядке product/location. После этого возврат и
остаточный release не вводят инверсию locks с резервированием другого заказа.
Новые storage allocations при возврате не создаются. Возврат, release, закрытие плана
и заказа, movements, audit, outbox и сохранённый HTTP result коммитятся вместе.

Действия человека находятся вне транзакции PostgreSQL. SQL rollback не перемещает
коробки обратно: при расхождении физики и учёта требуется сверка, заказ остаётся pending.
Нельзя удерживать DB locks во время физического переноса.

## Конкуренция и повтор команд

Session задаёт actor; сервер проверяет складской ACL перед исполнением и каждым replay.
System admin без складской роли не получает доступ. Политики прав и HTTP ошибок —
[identity](identity.md) и соответствующие flow. Idempotency-Key сохраняет исходный
успешный результат, новый ключ не разрешает повторить терминальный эффект.

| Конкурирующие команды                           | Наблюдаемый результат                                                                                   |
| ----------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| Reserve двух заказов на последнюю штуку         | Первый commit получает товар, второй повторно проверяет available и отказывает без отрицательного stock |
| Pick и release                                  | Order lock и запрет release при открытом плане защищают одно количество                                 |
| Cancel и shipment posting                       | Order lock сериализует команды; cancel первым запрещает posting, posting первым сохраняет уже shipped   |
| Два shipment одной staged части                 | Только обеспеченный posting успешен, второй целиком откатывается                                        |
| Return одного заказа и reserve другого          | Полный общий порядок balance locks позволяет обеим допустимым командам завершиться без deadlock         |
| Повтор confirm-return после неизвестного ответа | Исходный ключ возвращает сохранённый результат; второго движения нет                                    |

Автоматического retry SQL-транзакций нет. Handler effects и commit/rollback подробно
описаны в [transactions](transactions.md) и владельцах flow.

## Ограничения и будущие решения

Нет TTL/expiration, cron или worker job снятия резервов по возрасту. Добавление TTL
требует нового согласованного решения B4 с правилами для storage/staged и гонками.
Блокировка товарной позиции из-за физической нехватки, произвольная корректировка
stock и клиентские возвраты не реализованы. Они требуют отдельной бизнес-политики.
Нет кросс-складского исполнения, подмены SKU, партий/серий или дробных количеств.

HTTP body limit — 262144 bytes независимо от числа строк. ReceivingPosted v1 имеет
собственный предел 262144 UTF-8 bytes на envelope с payload. Версии/cursors — bigint,
ограниченный Number.MAX_SAFE_INTEGER, а не int4 quantity. Applied migrations и
опубликованные event schemas не меняются задним числом; несовместимое изменение
требует новой миграции/версии и плана совместимости.
