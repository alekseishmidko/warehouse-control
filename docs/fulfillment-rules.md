# WMS-201: правила заказа, резерва, сборки и отгрузки

**Бизнес-решения B1–B4 приняты 2026-10-29. WMS-204 реализует заказ/резерв/release/cancel по ADR-0022; picking/shipping остаются проектом.**
Основание — явное подтверждение владельца продукта: «WMS-201.2 — принимаем твое
предложение», «WMS-201.3 — принимаю твое предложение». Приняты частичные сборка/отгрузка,
учёт найденного при нехватке без автоматического списания, отмена с физическим возвратом
собранного и отсутствие автоматического истечения резервов. Ограничения этапа 1 сохранены.

Документ — владелец бизнес-правил WMS-201. Обзор для менеджера находится в
[product](product.md), общие инварианты — в [domain](domain.md), будущие границы
сообщений — в [contracts/fulfillment](contracts/fulfillment.md), последовательности
и числовые критерии — в [flow](flows/fulfillment.md). Реализация запланирована
WMS-203–206 после identity; новых таблиц, API, событий и фоновых jobs здесь нет.

## Принятые решения

| ID  | Принятое правило                                                                                                                         | Альтернатива / граница решения                                                                  |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| B1  | Частичные сборка и отгрузка разрешены; неисполненный остаток заказа открыт                                                               | Варианты только полной сборки/отгрузки не выбраны                                               |
| B2  | Фиксировать найденное при сборке; недособранное остаётся в резерве до решения оператора                                                  | Полный отказ из-за самой нехватки не выбран; ошибка проверки/SQL по-прежнему откатывает команду |
| B3  | До сборки отмена освобождает резерв; после переноса — отмена с подтверждённым физическим возвратом в хранение; отгруженное не отменяется | Запрет любой отмены собранного не выбран; возврат от клиента — отдельный будущий процесс        |
| B4  | Автоматического истечения резервов в этапе 2 нет                                                                                         | При TTL нужно отдельно утвердить срок, область действия, переходы и гонки; сейчас они не заданы |

**Область согласования:** приняты перечисленные бизнес-политики, а не готовый API/DDL.
Названия состояний, дополнительная блокировка позиции при нехватке, детали компенсации
и лимиты новых документов ниже остаются проектом реализации. Они не считаются отдельно
утверждёнными только из-за принятия WMS-201.2/201.3; уточняются до зависимой реализации.

## Область и количественная модель проекта

Один заказ относится к одному складу, строки уникальны по productId. Не предполагаются
кросс-складское исполнение, backorder в поставку, подмена SKU, партии/серии, дроби,
пересорт, автоматический выбор правил списания недостачи или клиентские возвраты.
Заказ может оставаться открытым при недостатке доступного товара; сам недостаток не
создаёт отрицательных балансов. Команда резервирования указывает фактические количества,
выполняется атомарно; автоматическое частичное резервирование без явного результата
не предлагается. Конкретные алгоритм выбора ячеек и schema — задача WMS-204.

По каждой строке заказа:

`ordered = open + reservedStorage + reservedShipping + shipped + cancelled`.

Здесь `open` — ещё не покрытый действующим резервом остаток; собранное уже находится
в `reservedShipping`, повторно учитывать его в `reservedStorage` нельзя. Все слагаемые
неотрицательны. `shipped` и `cancelled` — накопленные терминальные количества. Заказ
не меняет requested quantity задним числом ради закрытия недостачи.

Allocation — часть резерва конкретной строки заказа на конкретном balance. Для одного
логического резерва: `allocated = active + consumed + released`; active распределён
между storage/shipping. Разделение/перенос allocation не является новым независимым
резервом и не удваивает active. При частичной сборке переносится только фактическая часть.
Как физически хранить сегменты, определит schema WMS-204/205 с сохранением этого равенства.

На каждом balance `reserved = сумма active allocations` и `available = onHand-reserved`.
Для резервирования разрешены только доступные storage-позиции; receiving/shipping
не участвуют в подборе свободного товара. Для позиции с зарегистрированной физической
нехваткой проект предлагает блокировать новое резервирование/сборку до проверки.
Это **отдельное открытое уточнение B2**, не существующий флаг в БД; арифметическое
available остаётся показателем учёта, а доступность к резервированию может быть нулевой.
Без такого ограничения нельзя выдавать сомнительный физический остаток новым заказам.

## Переходы заказа — проект B1/B3

Предлагаемые состояния: `draft`, `active`, `partially_shipped`, `cancel_pending`,
`completed`, `cancelled`, `closed`. Точное хранение состояния/счётчиков проектируется
позже; статус подтверждается командой в транзакции, не одним доставленным событием.

| Из                         | Команда / условие                                            | В                                     | Эффект                                                                         |
| -------------------------- | ------------------------------------------------------------ | ------------------------------------- | ------------------------------------------------------------------------------ |
| draft                      | Подтвердить корректные строки                                | active                                | Состав фиксируется, stock не меняется                                          |
| draft                      | Отменить                                                     | cancelled                             | Резервов и движений нет                                                        |
| active                     | Резерв/частичная сборка без отгрузки                         | active                                | Меняются количества, не требуется отдельный статус на каждый этап              |
| active / partially_shipped | Провести shipment, остаток ещё открыт                        | partially_shipped                     | shipped увеличивается; если остаток active не покрыт, он остаётся open         |
| active / partially_shipped | Провести последнее количество, cancelled=0                   | completed                             | Всё ordered отгружено, активных резервов нет                                   |
| active / partially_shipped | Отменить остаток, shipping allocations нет                   | cancelled при shipped=0, иначе closed | Освобождаются storage allocations, остаток помечается cancelled                |
| active / partially_shipped | Отменить остаток, есть shipping allocations                  | cancel_pending                        | Блокируются новые reserve/pick/ship; stock ещё не возвращён, резервы сохранены |
| cancel_pending             | Подтверждён полный возврат собранного и освобождение остатка | cancelled при shipped=0, иначе closed | Возврат shipping→storage и release атомарны; уже shipped не меняется           |
| cancel_pending             | Ошибка возврата/неподтверждённое физическое действие         | cancel_pending                        | Учётный эффект не фиксируется; требуется разбор оператором                     |

`completed` означает всё отгружено; `cancelled` — ничего не отгружено и остаток отменён;
`closed` — часть отгружена, остальное отменено. Различие не позволяет назвать частично
исполненный заказ полностью отменённым. Смена принятых B1/B3 потребует явного нового
решения и пересмотра таблицы; schema/API не реализованы.

Запрещены все неуказанные переходы, в частности terminal→active, draft→completed,
active→completed без shipment и cancel_pending→shipping. Прежний Idempotency-Key
возвращает исходный успешный snapshot; новый ключ на терминальный объект — конфликт,
а не повторная запись эффекта. Изменить состав активного заказа/отменить shipped нельзя.

## Переходы задания сборки — проект B1/B2

Задание планирует только уже зарезервированное количество storage; оно не создаёт резерв.
`planned = pickedTotal + cancelledUnpicked + remaining`. pickedTotal — исторически
подтверждённая сборка; последующий возврат при отмене не стирает этот факт.

| Из                             | Команда / условие                                           | В                     | Учётный результат                                                       |
| ------------------------------ | ----------------------------------------------------------- | --------------------- | ----------------------------------------------------------------------- |
| ready                          | Подтвердить часть, есть remaining                           | in_progress           | Фактические stock и allocation переносятся storage→shipping             |
| ready / in_progress            | Подтвердить весь remaining                                  | completed             | remaining=0, сборка завершена, отгрузки ещё может не быть               |
| ready / in_progress            | Подтвердить найденное меньше ожидаемого и сообщить нехватку | shortage              | Найденное переносится только при B2; недособранный резерв не исчезает   |
| shortage                       | Проверка завершена, остаток доступен                        | ready или in_progress | Возобновление после проверки; повторного движения уже picked нет        |
| ready / in_progress / shortage | Отменить неисполненную часть                                | cancelled             | Только оставшиеся storage allocations освобождены; собранное требует B3 |

`actual` для движения всегда >0; сообщение о нехватке с actual=0 не создаёт нулевого
движения и само не изменяет balance. Команда больше remaining/active reservation
отклоняется целиком. completed/cancelled нельзя снова собирать. shortage не разрешает
автоматическую корректировку onHand, замену SKU или освобождение чужого резерва.

При B2 сама нехватка не отменяет подтверждение найденного количества. Ошибка прав,
валидации или SQL всё равно откатывает всю команду; физическое расхождение требует
отдельного разбора и не становится неявным списанием.

## Переходы резерва — проект уточнения модели

Общий инвариант active→consumed/released из domain сохраняется для однородных закрытий.
Для частично consumed, частично released количества предлагается явный терминальный
`closed_mixed`, чтобы не выдавать частичное исполнение за полностью consumed/released.
Это открытая часть проекта B1/B3, schema/state enum ещё нет.

| Из     | Действие                                                    | В                    | Balance / количество                                     |
| ------ | ----------------------------------------------------------- | -------------------- | -------------------------------------------------------- |
| Нет    | Резервировать доступное storage                             | active               | reserved += q; onHand прежний                            |
| active | Перенести часть при сборке                                  | active               | active переносится между locations; общий резерв прежний |
| active | Частично отгрузить                                          | active пока active>0 | onHand/reserved shipping -=q, consumed+=q                |
| active | Освободить часть storage или подтверждённо вернуть shipping | active пока active>0 | released+=q, reservation уменьшается на q                |
| active | Последняя часть consumed, released=0                        | consumed             | active=0, allocated=consumed                             |
| active | Последняя часть released, consumed=0                        | released             | active=0, allocated=released                             |
| active | Последняя часть закрыта, consumed>0 и released>0            | closed_mixed         | active=0, обе причины закрытия сохранены                 |

Запрещены consumed/released/closed_mixed→active, повторное потребление закрытой части,
перенос без active allocation, release уже shipped и прямой release shipping без B3.
Освобождение само не создаёт физическое движение; компенсационный возврат создаёт пару.

## Переходы отгрузки — проект B1/B3

Каждый shipment — отдельный неизменяемый документ фактической партии одного заказа,
одного склада. Частичный shipment проводится полностью по своему составу; «частично
проведённый shipment» не нужен. При B1 возможно несколько posted shipment на заказ.

| Из     | Команда / условие                                                         | В                  | Эффект                                                                    |
| ------ | ------------------------------------------------------------------------- | ------------------ | ------------------------------------------------------------------------- |
| Нет    | Создать документ выбранных staged quantities                              | draft              | Stock не меняется, второй резерв не создаётся                             |
| draft  | Провести, все строки покрыты активными shipping allocations своего заказа | posted             | onHand/reserved -=q, allocations consumed; движения/audit/outbox атомарны |
| draft  | Отменить документ                                                         | cancelled          | Stock/резерв остаются прежними, заказ не отменяется автоматически         |
| draft  | Не хватает staged / заказ заморожен / данные неверны                      | draft после отказа | Весь posting rollback, успешные строки отдельно не фиксируются            |
| posted | Тот же Idempotency-Key                                                    | posted (replay)    | Исходный response, нового списания нет                                    |

Запрещены posted→draft/cancelled, cancelled→posted, отгрузка напрямую из storage,
отгрузка чужого allocation и q больше остатка строки заказа. Несколько draft не
создают дополнительного обеспечения; каждый posting повторно проверяет покрытие
под блокировками. Возврат уже отгруженного — новый будущий процесс, не отрицательный shipment.

## Отмена, физический возврат и гонки

Проект B3 отменяет **весь неотгруженный остаток** заказа; отмена произвольной части
строки — отдельное пока не согласованное расширение. При наличии staged сначала
cancel_pending сохраняет allocations и замораживает исполнение. Оператор физически
возвращает товар в разрешённые storage-ячейки того же склада, затем подтверждает полный
вектор возврата. Одна короткая транзакция проверяет целевые балансы/границы int4,
переносит stock shipping→storage, освобождает резерв и закрывает неотгруженный остаток.

Физическое действие не находится внутри DB-транзакции. Ошибка SQL не возвращает коробку
назад: при расхождении физики и учёта заказ остаётся cancel_pending и требуется сверка.
Нельзя держать блокировку PostgreSQL во время действий человека. Конкретные return DTO,
компенсационные движения и полномочия уточняются WMS-202/206 по утверждённому правилу.

Владельцем команды выступает fulfillment service, меняет stock/reservations только
публичный inventory service в том же context. Сериализуются order/header, задания,
allocations и balance-ключи в детерминированном порядке; SQL-порядок реализуется позже.

| Гонка                                   | Побеждает первая фиксация           | Что делает вторая команда                                                                    |
| --------------------------------------- | ----------------------------------- | -------------------------------------------------------------------------------------------- |
| Reserve двух заказов на последнюю штуку | Один reserve                        | Вторая повторно проверяет available и отказывает без отрицательных остатков                  |
| Release storage и pick той же части     | Release либо перенос allocation     | Pick после release отклоняется; release после pick требует возврата из shipping              |
| Cancel и posting shipment               | Order lock + состояние после commit | Cancel первым запрещает shipment; shipment первым остаётся posted, отменяется только остаток |
| Два shipment одной staged части         | Один posting                        | Второй не имеет active allocations, полностью rollback                                       |
| Повтор confirm-return после timeout     | Один успешный HTTP result           | Тот же key replay; новый key не возвращает тот же товар второй раз                           |

## Истечение резервов: принятое правило B4

Принято для этапа 2: **нет автоматического expiration**. Нет expiresAt как обещания,
TTL, cron/worker job или команды «снять просроченные», которую можно считать готовой.
Возраст резерва может быть диагностикой, но не основанием уменьшить reserved.
Резерв прекращается только явным release/cancel или shipment consumption.
Следовательно, expiration↔picking/shipping исключена из текущего объёма реализации;
гонки явных release/cancel разобраны выше. Само время не освобождает товар в shipping.

Добавление TTL в будущем будет изменением принятого B4, а не выполнением скрытого
требования. До такой реализации отдельно согласуются срок/часы БД, применимость к storage
и staged, приоритет с pick/ship и атомарность recheck под теми же order/allocation/balance
locks. Сейчас не добавлять expiresAt, timer, cron или job освобождения по возрасту.

## Подтверждённые границы этапа 1

- Quantity: SQL int4 и целый JS number; delta операции 1..2147483647, balance/counters
  0..2147483647, `0<=reserved<=onHand`. Проверки до SQL и CHECK в SQL дополняют друг друга.
- Receiving: 1..1000 различных productId; quantity каждой строки в указанном диапазоне.
  Предел не означает, что допустим любой суммарный stock: результат каждой позиции тоже ограничен.
- ReceivingPosted v1: всё сообщение JSON UTF-8 <=262144 bytes с envelope/unknown fields.
  HTTP JSON parser: лимит 256*1024 bytes тела; это отдельная граница, не вычет envelope.
  Документ на верхней границе строк всё равно обязан пройти предел bytes события.
- Aggregate versions/cursors: bigint с CHECK до Number.MAX_SAFE_INTEGER, не int4 quantity.
- Нет сужения/расширения существующих схем, новых migrations или новой версии ReceivingPosted.
  Breaking quantity/shape/semantics change опубликованной версии потребует новой major schema
  и плана миграции/совместимости, изменение SQL — новой миграции, не правки applied SQL.

Проверяемые источники: [quantity](../apps/backend/src/shared/quantities/quantity.ts),
[ReceivingPosted schema](contracts/events/receiving.receipt-posted.v1.schema.json),
[HTTP parser](../apps/backend/src/infrastructure/http/configure-http.ts),
[контрактные unit-проверки](../apps/backend/test/unit/event-contracts.spec.ts).
Предлагаемые лимиты **новых** order/shipment документов — [отдельный draft контракта](contracts/fulfillment.md).
