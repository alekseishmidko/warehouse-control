# WMS-202: идентификация, сессии и доступ

Документ для менеджера, разработчика и оператора. **2026-10-29 владелец продукта
принял логин/пароль с серверной сессией и threat assumptions**, см. [ADR-0018](adr/0018-server-sessions.md).
В тот же день отдельно утверждена матрица ролей/складов — [ADR-0019](adr/0019-warehouse-role-matrix.md).
Сроки по умолчанию остаются предложением; runtime требует явные значения.
WMS-202 реализована: users/sessions, auth endpoints и policies, без dev actor fallback.

## Что принято

Аутентификация проверяет личность, сессия узнаёт её в следующих запросах, авторизация
проверяет конкретное действие над объектом. Принят вариант локального логина/пароля
с серверным состоянием сессии в PostgreSQL. Отдельный JWT access/refresh механизм,
OIDC provider и Redis для этого этапа не выбраны. Идентичность actor формирует сервер,
не body/headers клиента. Публичный deployment этим решением не разрешён.

Пароль должен храниться в виде безопасного password hash, а не открытым текстом или
обратимым шифрованием. Браузерный session token — случайный секрет; для lookup сессии
хранится его хеш в БД, без сырого token в таблицах/логах. Используются scrypt N=2^17/r=8/p=1, 256-bit token и отдельные schemas/миграции WMS-202.2.
Это разные задачи: быстрый digest случайного token не заменяет password hashing.

Браузерная сессия передаётся HttpOnly cookie. Реализованы exact Origin/JSON/CSRF,
Secure cookie для HTTPS и явный dev/test loopback HTTP. CORS не включён. Подробности
[реализованной policy](flows/identity.md#cookie-csrf-и-current-user). Приложение не завершает
TLS: внешний доступ требует отдельного HTTPS gateway. Не отключать защиту ради внешнего стенда.

## Принятые threat assumptions

Threat assumptions — границы доверия и возможности нарушителя. Проверки соответствуют WMS-202, но не обещают защиту от DBA/host compromise или готовый TLS gateway.

| ID  | Предположение / угроза                                           | Требование                                                                         | Проверка / граница                                                                        |
| --- | ---------------------------------------------------------------- | ---------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| T1  | Любой HTTP-клиент может подделать запрос и обойти UI             | Не доверять actor/ролям/status/reserved из body; DTO и auth обязательны на backend | Подставленные actor/role не дают полномочий                                               |
| T2  | Пользователь знает UUID чужого документа или склада              | Определять склад самого объекта и проверять доступ к нему; UUID не разрешение      | Чужой receipt по ID, чужие списки и commands недоступны                                   |
| T3  | Пароль могут подбирать                                           | Ограничивать попытки входа; ответ не раскрывает наличие логина                     | Одинаково безопасный отказ неверных credentials; проверка ограничения попыток             |
| T4  | Session token может быть украден                                 | Срок/отзыв, защита cookie, отсутствие секретов в логах/URL/ответах диагностики     | Expired/revoked session даёт 401; cookie/token не утекли                                  |
| T5  | Сторонний сайт может послать запрос с cookie                     | Проверять CSRF на изменяющих операциях, включая выбранную защиту login/logout      | Межсайтовая команда не меняет БД                                                          |
| T6  | Доступ/роль/активность пользователя меняются после login         | Не считать права навсегда сохранёнными при входе; проверять на каждой попытке      | Отзыв доступа запрещает новую команду и replay старого key                                |
| T7  | DB/host admin способен читать/менять данные напрямую             | Не обещать защиту от полного захвата инфраструктуры; секреты/grants вне исходников | Ограничение модели, а не тест «защиты от DBA»                                             |
| T8  | Внешняя сеть недоверенная                                        | HTTPS обязателен до внешней эксплуатации; доверять только явно настроенному proxy  | Cookie/proxy/origin policy проверена до публикации                                        |
| T9  | Dev actor способен обойти настоящую auth, если оставить fallback | Убрать обход в production/business graph при внедрении identity                    | Env/body/header не включают обход auth; tests/gate используют явную тестовую идентичность |

Проверка роли на запросе не обещает отменить уже committed команду и не определяет
автоматически судьбу начавшейся до отзыва транзакции. Точка проверки под user/session SHARE locks и ожидание admin UPDATE зафиксированы
в flow и проверены integration tests. Уже допущенная команда может завершиться до revoke.
Секреты не логируются и при отказе входа, CSRF, SQL или закрытии ресурсов.

## Роли и складская матрица

Матрица **утверждена владельцем продукта 2026-10-29**, и реализована для существующих endpoints.
Основание — «утверждаю матрицу взаимодействия», см. ADR-0019. Таблица описывает
правила; будущие endpoints складского процесса не добавлены только ради матрицы. Складские назначения приняты как `(userId, warehouseId, role)`; system_admin —
отдельная системная роль. Нет роли по умолчанию, предоставляющей все склады.

| Создать/провести приёмку                          |   —    |         ✓          |       —       |          ✓           |      —       |

| Резервировать/release несобранного                |   —    |         —          |       ✓       |          ✓           |      —       |
| Подтвердить фактическую отгрузку                  |   —    |         ✓          |       —       |          ✓           |      —       |
| Запросить отмену заказа                           |   —    |         —          |       ✓       |          ✓           |      —       |
| Подтвердить физический возврат собранного         |   —    |         ✓          |       —       |          ✓           |      —       |
| Провести разрешённую корректировку недостачи      |   —    |         —          |       —       |          ✓           |      —       |
| Читать бизнес-аудит своего склада                 |   —    |         —          |       ✓       |          ✓           |      —       |
| Управлять пользователями/назначениями             |   —    |         —          |       —       |          —           |      ✓       |
| Отозвать чужие сессии                             |   —    |         —          |       —       |          —           |      ✓       |

Принято: system_admin не получает бизнес-действия автоматически; для приёмки ему
тоже нужна отдельная warehouse role. Это разделяет полномочия, но не означает защиту
от системного администратора, имеющего право назначать роли. Изменения назначений аудитируются, admin-набор защищён advisory lock и проверкой
последнего active system_admin; это не защита от владельца DB/host.

Пример: Иван — operator склада A и viewer склада B. Для действия на B нельзя объединить
«operator где-то» и «есть доступ к B»: проверяется одна подходящая роль именно на B.
В списках фильтрация должна ограничивать видимые склады; получение объекта по UUID
также требует проверки. Корреляция и Idempotency-Key не являются полномочием.

Глобальный catalog, управление складами, системный аудит и outbox recovery требуют
отдельных явных permissions до появления соответствующих административных API.
Текущая PostgreSQL warehouse_outbox_admin — техническая permission group, не роль
пользователя. Локальный CLI сейчас проверяет OS/DB-доступ, а operator UUID сообщает
вызывающий; это нельзя объявить аутентификацией человека. Возможный admin HTTP не готов.

## Сроки сессий — предложение, ожидает ответа

Ранее предложены: absolute timeout 12 часов от входа и idle timeout 30 минут.
Продление idle не должно отменять абсолютную границу. Числовые defaults пока не утверждены. Реализация требует оба значения явно
(30..86400 секунд, idle<=absolute), без их автоматической подстановки.
Session timeout не относится к товарным резервам: принятое B4 WMS-201 по-прежнему
исключает автоматическое освобождение stock reservation по времени.

Logout отзывает текущую сессию в БД; блокировка пользователя/смена пароля отзывает
все его сессии. Первый администратор создаётся отдельной bootstrap CLI, не публичной
регистрацией/универсальным default password. Подробности и команды — в flow.

## Реализованное исполнение и API

Подробные последовательности, границы commit/rollback, locks/revoke, bootstrap и примеры:
[владелец flow](flows/identity.md). Публичные login/logout/me и admin users/grants/revoke
подключены; [README модуля](../apps/backend/src/modules/identity/README.md) содержит пути,
DTO/schema карту и ограничения. OpenAPI генерируется из production controllers.

Role checks выполняются заново внутри context до idempotency claim/replay. Identity admin
mutations и безопасный audit атомарны. Bootstrap — отдельная one-time stdin CLI с DB group
и retained marker, не публичная регистрация. Dev actor удалён из production graph;
DEV_ACTOR_ENABLED=true даёт отказ конфигурации во всех режимах.

## Статус и первичные источники

Реализованы WMS-202.2–202.6; числовой default TTL не утверждён, поэтому оба срока задаются
оператором явно. Тестовые значения не являются выбором production policy. Backend без них
не стартует. Резервы stock не истекают автоматически по B4, независимо от срока сессии.
[Отчёт](reports/wms-202.md) фиксирует реальные проверки; внешнего deployment/TLS gateway,
MFA/SSO/password recovery UI нет.
