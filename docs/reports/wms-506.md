# WMS-506: переключение транспорта и возврат

## Задание до реализации

Источник — поручение пользователя взять следующий этап плана, WMS-506.1–6.
Source task — [wms-506.json](../tasks/wms-506.json). Результат — воспроизводимая
репетиция на disposable PostgreSQL/Kafka и operator runbook. Рабочая БД, .env,
volumes и внешний deployment в объём не входят.

Участник — локальный оператор dev-стенда с admin-доступом к disposable контейнерам.
Вход — синтетические документы через production services и HTTP с session/CSRF/ACL.
Kafka records проходят прежнюю валидацию и retained identity. Backup содержит данные
БД и считается приватным; credentials/raw envelopes не выводятся в отчёт.

Предусловия: Docker доступен, migrations применяются к новой БД, mTLS Kafka доступна,
API и consumers можно остановить, retained история полна. На время границы остановлены
все writers, а не только UI. Успех — pending set применён, marker/cursor сохранены,
inventory сверена; возврат после новых effects не восстанавливает старую БД.

Инварианты: immutable eventId/envelope, тот же inventory.putaway, отсутствие двойных
tasks/movements, reserved=SUM(active), allocation conservation, commit перед offset ack.
Ошибки backup/restore, gap/retention, dead/quarantine, активный lease или расхождение
сверки запрещают открыть запись. Нет skip, очистки markers и offset reset для обхода.

Новое бизнес-правило не вводится. Технический выбор — сохранить local deliveries для
обратного переключения и полный retained replay publisher, как требует ADR-0034.
Это replay транспортных записей; бизнес-обработке передаётся только pending set.
Markers исторических документов исключают повторное применение. Нельзя называть
этот режим публикацией только pending records или уже выполненным production cutover.

## Реализация и трассировка

Подробности исполнения, Mermaid, доверие к входу, SQL, запуск, отказ и возврат имеют
одного владельца: [transport-cutover flow](../flows/transport-cutover.md).
Нового runtime maintenance flag, endpoint или migration не добавлено. Реализация этапа —
воспроизводимая operator rehearsal существующих production protocols и проверяемый
SQL snapshot, а не новый transport engine. ADR-0038 уточняет cutover-раздел ADR-0035.

| AC        | Реализация                                                                             | Проверка                                                                                                                                                                               |
| --------- | -------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| WMS-506.1 | transport-boundary.sql + verifyCutoverBackup                                           | pg_dump custom archive, restore в новую БД; полный snapshot до/после совпадает; SHA256/bytes сохранены                                                                                 |
| WMS-506.2 | freezeApi, start/stopLocalWorker, assertSafeBoundary                                   | Новое соединение HTTP отклонено; SIGTERM/exit0 worker; checks.activeLeases=0; отдельный test отвергает активный claim                                                                  |
| WMS-506.3 | Существующие PublisherService/ApplicationConsumerService, сохранённые local deliveries | Historical replay не меняет local deliveries/старые markers; task count растёт ровно на pending set; event identities не изменяются                                                    |
| WMS-506.4 | startPublisher/startConsumer/drainPublisher/waitForEffects                             | Второй singleton отвергнут; backlog применён до api.listen; unchanged stock/movements                                                                                                  |
| WMS-506.5 | receiveThroughHttp/completeWarehouseFlow, настоящий Kafka duplicate/outage             | HTTP receipt+saved replay → putaway → reserve → pick6 → ship4 → cancel/return2; closed_mixed; broker outage сохраняет business commit; offset подтверждает duplicate без нового effect |

Все строки проверяет `kafka-cutover.spec.ts :: 506 backup and bidirectional cutover`.
Отказ при active lease — `506 boundary rejects an active claim before transfer`.
N+1 отдельно проверяет существующий `kafka-consumer.spec.ts :: 504.6: Kafka starts at
N+1 after local completion`: это technical stream/handler, не повторное posting
реальной приёмки. Lost ack/crash/rebalance — существующие реальные suites503/504/505,
исполняемые итоговым check:pr. Не выдаём один receipt version1 за доказательство N+1.

## Review → refactor → повторное review

Просмотрены новые suite/fixture/SQL, package entrypoints и связанные worker/publisher/
Kafka application protocols, действующие ADR и recovery boundaries.

- P2, первоначальный cleanup suite: параллельный close consumer и HTTP graph мог закрыть
  pool до завершения handler. Исправлено: последовательный cleanup consumer → publisher
  → worker → API, ошибка каждого close сохраняется, остальные ресурсы тоже закрываются.
- P3, первый SQL snapshot: не показывал transport cursors и attempts отдельно от
  application cursor. Добавлены transportStreams/deliveries; тест сравнивает неизменность
  local scheduling после Kafka handover и равенство restore snapshot.
- Уточнена документация N+1: реальный receipt сейчас имеет один posting fact. В качестве
  доказательства continuity ссылаемся на отдельный protocol test, а не на новый бизнес-факт.

Повторное review проверило отсутствие direct stock writes, секретов/envelope в report,
reset markers/cursors/offset и restore старого backup поверх новых effects. Складская
логика переиспользована через owners, SQL snapshot общий для test и operator runbook.
Новых подтверждённых дефектов в просмотренной области после исправлений не выявлено.
Это не независимый аудит всего проекта и не доказательство отсутствия любых гонок.

Первый полный harness остановился на coverage guard при699успешных backend tests и54web:
kafka-startup.ts branches94.44 < baseline94.73. HTML показал непроверенный coordinator
deadline. Добавлен детерминированный unit case `506 coordinator deadline refuses startup
without joining or acknowledging offsets`: при недоступном coordinator на deadline
startup запрещён, group join/handler/offset ack не выполняются. Монотонные часы управляются
в тесте; реальные15s не ожидаются. Runtime и baseline не менялись. Итоговый harness
повторяется на исправленном snapshot; прежний failed run не считается evidence готовности.

## Ограничения

Рабочий kind/Strimzi стенд не переключался; автоматическая репетиция использует
Testcontainers Kafka mTLS и disposable PostgreSQL. Отдельный внешний deploy не разрешён.
Restore проверен в новой БД того же server с уже созданными roles. Disaster restore
на новый server, retention gap/произвольный poison, несколько publisher replicas,
HA, новые consumer names/partition topology и key custody production остаются вне объёма.
Существующий publisher dead не снимается Kafka quarantine CLI: stop и отдельное
reviewed recovery действие. Никакого автоматического bypass в cutover не добавлено.
