# WMS-104: минимальные складские данные

Отчёт реализации от 2026-10-19. Все шесть шагов выполнены; следующий — WMS-105.

## Реализовано

CatalogService/Repository, WarehousesService/Repository и InventoryService/Repository,
DTO в отдельных папках, без публичных HTTP CRUD. Product, Warehouse, Location,
StockBalance, StockMovement описаны собственными schemas и новыми migrations
0003_charming_satana.sql и 0004_inventory-permissions.sql. Прежние SQL не изменялись.

Количество — int4, 0..2147483647 для остатков и 1..MAX для прихода. Общий source
constant используют service/SQL/audit; уточнён максимум неопубликованной v1 event schema.
Actor/correlation/reason metadata и повторяемые UUID/code/name проверки вынесены
в shared без зависимостей от бизнес-модулей.

Начисление в receiving location использует guarded SQL upsert и сохраняет
movement/audit в том же context. Movement operationId unique; повтор — reject
с полным rollback, не возврат прежнего результата. Движения immutable для runtime
и обычного DML владельца; admin способен отключить защиту.

Dev-only CLI db:seed создаёт товар/склад/три ячейки через сервисы, не начисляет stock,
закрывает pool и не работает при test/production. Fixture builder переиспользуется tests.

## Проверки

pnpm test: **105 тестов, 9 suites** (49 unit, 56 integration), реальный PostgreSQL
из Testcontainers, та же версия/digest, что Compose. Build и компиляция tests
выполнены перед прогоном.

Проверены:

- Две транзакции синхронизированы barrier после чтения отсутствующего balance;
  приходы 2+3 дают одну строку с onHand=5 и два движения.
- MAX принимается, MAX+1/дробь/строка/NaN/0 отклоняются; concurrent overflow
  оставляет только одно безопасное начисление.
- Duplicate operationId не оставляет второй прибавки/audit/movement.
- Неизвестный товар, чужая/несуществующая/не receiving ячейка и invalid audit
  не оставляют частичных записей.
- FK warehouse/location, unique SKU/stock key/location code, reserved/onHand CHECK
  действуют и при raw SQL. Runtime receipt выполняется под warehouse_app.
- Movement UPDATE/DELETE/TRUNCATE запрещены runtime и обычному SQL владельца.
- Ошибка после audit/movement откатывает весь приход. Dev CLI дважды создаёт
  независимые demo sets без stock; отказ вне development проверен до подключения.
- Старые HTTP/context/audit/lifecycle проверки сохраняются. Новый FK movement→audit
  потребовал включить обе таблицы в прежний owner TRUNCATE test: иначе FK precheck
  возвращает 0A000 раньше append-only trigger. Проверка trigger сохранена.

Полный JSON Schema validator/type generation не реализованы: unit сверяет именно
numeric boundary и валидность quantity имеющегося примера. Это не завершение WMS-105.
Typecheck прошёл. Повторная schema generation: no schema changes.
Ссылки, JSON, file-level docs и каталог 131 собственного файла проверены.
После прогона временных PostgreSQL-контейнеров с test label не осталось.

## Границы

Dev Compose не мигрировался и реальные dev fixtures в него не добавлялись:
все data/CLI проверки выполнялись на disposable containers. Auth, документы
приёмки, outbox, reservations, размещение, компенсации, shipping и публичный stock API
ещё не реализованы. Dev admin URL не является production runtime login.
