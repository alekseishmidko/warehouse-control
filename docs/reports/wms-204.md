# WMS-204: заказ и резервирование

Реализовано 2026-10-31 по явно согласованному [ADR-0022](../adr/0022-order-reservations.md).
[Полный flow с Mermaid, SQL, commit/rollback и evidence](../flows/reservations.md),
[модуль](../../apps/backend/src/modules/fulfillment/README.md).

## Реализованы все шесть пунктов

- WMS-204.1: orders/order_lines, draft→active/cancelled, immutable состав, typed DTO и HTTP API.
- WMS-204.2: storage своего склада/SKU, сортировка productId/locationId, FOR UPDATE без SKIP LOCKED.
  User/session policy → key → order → balances; GET использует тот же порядок и order SHARE.
- WMS-204.3: allocations и reserved изменяет inventory, под общим context fulfillment;
  audit каждого allocation, order audit, OrderChanged и saved HTTP result коммитятся вместе.
- WMS-204.4: explicit partial release по allocationId, retained allocated/active/released;
  cancel до сборки освобождает всё и закрывает заказ. Никаких TTL/expiresAt/jobs.
- WMS-204.5: реальные PostgreSQL concurrency/rollback tests, две наблюдаемые lock waits,
  несколько ячеек, explicit partial reserve, недостаток многострочного запроса, reserve↔release.
- WMS-204.6: независимый SUM(active) vs reserved SQL, CHECK диапазонов, deferred checks полного ledger
  и тест прямого несовпадения 23514. Нет отрицательных quantity/reserved/active.

## Ошибки, найденные проверками

Проверки поймали обращение shared deferred function к полю NEW.line_id на stock_balances:
исправлена структурная ветка PL/pgSQL до применения миграции в dev БД. Release DTO был
class instance для canonical JSON fingerprint: исправлено преобразованием в явный plain JSON.
SQL barrier test требует немедленно запускаемых Supertest promises, а не lazy request objects.
В финальном прогоне все соответствующие ветки прошли.

## Границы

Нет picking/shipping/consumed и staged return, UI, expiration/purge, FIFO или межскладского
исполнения. Allocation history в GET пока не пагинируется. Migration 0025 закрывает исключение для balances без allocation history:
INSERT/UPDATE любой позиции сверяется с SUM(active), существующие расхождения блокируют миграцию.
Сверка всех balances проверяется отдельно SQL; DBA способен обойти guards.
OrderChanged содержит orderId/action, quantities объясняет immutable audit и allocation history.
Consumers order aggregate пока нет: retained outbox факт не означает внешнюю delivery;
новая подписка требует replay/start-position плана. Auth policy осталась явно конфигурируемой.
Следующая задача — WMS-205: сборка заказа.

## Исправление P2 reconciliation

Новая migration 0025_strict_reservation_reconciliation.sql, без редактирования 0024:
полная предварительная сверка под table locks, unconditional balance/ledger check и AFTER
INSERT OR UPDATE deferred trigger. При legacy mismatch — 23514/rollback migration, без
автоматического изменения quantity и без выдумывания оснований. Два отрицательных integration
cases под warehouse_app проверяют ошибку именно COMMIT и отсутствие durable mismatch.
Отдельный case проверяет preflight mismatch; корректные reserve/release/cancel покрывает
существующий полный PostgreSQL suite. Synthetic putaway receiving reserve существует только
в rollback-only callback: реальный невалидный ledger между запросами не сохраняется.

Финальная проверка исправления: `pnpm typecheck`, `pnpm test` — **476 tests / 31 suites**,
`pnpm format:check` и `git diff --check` прошли. Миграция 0025 применена на локальном
PostgreSQL 17.9; повторный `pnpm db:migrate` и `pnpm db:check` прошли. Данные/volume
не удалялись, 0024 не редактировалась. Docker gate в этом исправлении не повторялся;
проверки новых SQL guards выполнены реальными migrations в PostgreSQL Testcontainers и dev БД.
