# WMS-110: первый durable handler размещения

Отчёт реализации 2026-10-26. Production worker создаёт pending PutawayTask из ReceivingPosted,
физическое перемещение и UI задач не входят в этот этап.

| Шаг   | Результат                                                                                                         |
| ----- | ----------------------------------------------------------------------------------------------------------------- |
| 110.1 | Inventory-owned PutawayTask, global unique source line/event-line и composite source FK                           |
| 110.2 | ReceivingPostedHandler → публичный InventoryService.createPutawayTasks, без receive/credit/movement               |
| 110.3 | Stable inventory.putaway зарегистрирован в production graph, полный receipt stream; future known no-op dispatch   |
| 110.4 | Task/audit/processed marker/consumer cursor/transport cursor/completion фиксируются worker COMMIT B               |
| 110.5 | Дубликаты, actual row/unique locks, source conflict, SQL faults, two lines и actual child SIGKILL до/после commit |
| 110.6 | Подробный Mermaid flow, состояния pending/completed и исполняемая SQL связь receipt → event → task                |

## Проверено

- `pnpm --filter @warehouse/backend test:prepare` затем
  `pnpm --filter @warehouse/backend exec jest --runInBand`: **328 tests / 21 suites passed**,
  147 unit и 181 integration, реальные PostgreSQL 17 Testcontainers.
- Production build, event contracts generation diff, OpenAPI diff и compilation tests входят
  в test:prepare. Схема ReceivingPosted v1 и HTTP endpoints не менялись.
- `pnpm typecheck`: source/test TS. `pnpm db:generate`: no schema changes после новых snapshots.
- Migrations применяются на чистые disposable БД, повтор применения проверяется существующей
  outbox suite. Старые применённые SQL не менялись, dev volume не затронут.
- Production default registry в harness сохраняется без override; restricted warehouse_app
  реально создаёт tasks/audit/markers/cursors, UPDATE/DELETE/TRUNCATE task отклоняются.
- Все 18 новых файлов внесены в каталог, ссылки и git diff --check корректны;
  после финального прогона disposable integration containers отсутствуют.
- Read-only putaway-result.sql выполняется на happy path; assertions сверяют task source,
  server actor/correlation и stock=10/reserved=0/movement=1/event=1 после consumer.

Новые integration cases проверяют прямой inventory repeat без нового audit, controlled marker
replay, два processors с одним token и наблюдаемым lock wait, concurrent absent-key INSERT
с rollback loser audit, source mismatch и новый конфликтующий факт для уже запланированной line.
Fault AFTER audit/task/marker/consumer cursor/delivery completion/transport cursor и сбой второй
task откатывают весь consumer batch. Receipt stock при этом остаётся committed. После снятия
fault retry создаёт ровно необходимые tasks. Child tests SIGKILL-ят именно реальный production
handler до и после подтверждённого processing commit; отдельный worker восстанавливает lease
либо не выбирает уже completed delivery, двойного stock/audit/task эффекта нет.

No-op routing предусмотрен для будущих **известных** неинтересных типов. В текущем KnownEvent
только ReceivingPosted v1, поэтому adapter unit использует surrogate исключительно для проверки
dispatch ветки. Он не добавлен в runtime registry и не является end-to-end evidence нового
контракта. Unknown type/version по-прежнему dead до handler, что покрыто worker integration.

## Исправления, обнаруженные проверками

Первый generated DDL поставил FK раньше новых receiving unique keys. Только новые, ещё не
применённые artifacts были восстановлены и перегенерированы в последовательности:
0013 receiving keys → 0014 task/FK → 0015 permissions/retention. Ручной правки generated SQL
и старых applied migrations не было. Финальный общий прогон применил эту последовательность.
Существующий audit truncate test обновлён для нового FK graph: проверяет append-only trigger,
а не PostgreSQL FK precheck. Все проверки затем прошли, Docker skip/fallback не применялся.
