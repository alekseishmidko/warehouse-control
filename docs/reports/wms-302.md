# WMS-302: ресурсы приложения и миграции

## Требования до реализации

Вход: оператор с доступом к выбранному namespace передаёт chart, immutable image digest,
несекретные auth-настройки и имена заранее созданных Secrets. SQL credentials не
попадают в values или rendered manifests. Runtime и migrator используют разные
Secrets и service accounts без Kubernetes API token/RBAC. Бизнес-права задаёт session.

Предусловия: отдельные namespace и PostgreSQL с PVC установлены платформой. Chart
не устанавливает PostgreSQL. Результат: migration Job завершён до изменения
Deployments, API отвечает health, worker запущен. Ошибка миграции запрещает rollout,
сохраняет прежний release workload и Job diagnostics. Session lock сериализует CLI
во всех releases одной БД. Это не exactly-once исполнение Pod: повтор безопасен
через журнал SQL migrations. Applied SQL не меняется.

## Реализация и review → fixes → повторное review

- Chart 0.2: API/worker Deployments и API ClusterIP, ConfigMap, references на existing
  Secrets, отдельный migration account/Job. Все backend процессы запускаются одним
  image digest с разными entrypoints. Runtime UID 1000, read-only rootfs, drop ALL,
  no privilege escalation, seccomp, bounded /tmp и requests/limits.
- Migrator извлечён в applySerializedMigrations: один выделенный client удерживает
  session lock до journal lookup/SQL и уничтожается в finally. Shared бизнес-runner,
  applied SQL и transaction invariants не менялись. [ADR-0028](../adr/0028-kubernetes-release-migrations.md).
- Before hook создаёт migration account, затем revision Job. При неуспешном hook
  прежние Deployments не обновляются; сохранённый Job помогает recovery.
- При review исправлено имя Job для длинных releases (53 chars), добавлена schema
  проверки наличия requests/limits и запрещены одинаковые runtime/migration Secret names.
- Рефакторинг gate: от общего ожидания к проверке наблюдаемых Pod/Job состояний,
  failure diagnostics без Secret data, explicit recovery без SQL auto retry.
- Первые прогоны gate выявили реальный Docker Desktop/containerd import дефект:
  multi-arch index без чужих платформ не импортировался через kind --all-platforms.
  Исправление: PostgreSQL archive выбранной архитектуры, CRI canonical digest alias.
  Для backend gate сравнивает config hash из source archive с imported CRI image ID,
  затем использует нормализованный manifest digest во всех процессах. Нельзя брать
  image config ID за registry digest. Все временные archive/Secrets удаляются finally.
- После запрета одинаковых Secret names fault test был усилен: отдельный ошибочный
  Secret с runtime credentials действительно запускает Job, и gate проверяет
  Job.status.failed=1. Отказ Helm schema не подменяет отказ SQL migration.
- Повторное review проверило migration lock lifetime при SQL/file failure, journal
  после ожидания двух конкурентов, pre-hook ordering, разделение DB/Kubernetes прав,
  Secret rotation, rollback и cleanup. Новых замечаний в изменённых путях нет.

## Проверки и ограничения

Среда: Node 24.19.0, pnpm 10.18.3, kind 0.33.0, kubectl 1.37.0, Helm 3.22.0,
Kubernetes 1.37.0, PostgreSQL 17.9; macOS arm64/Docker Desktop. CLI tools из /tmp,
глобальные установки/context и рабочая .env не менялись.

- Целевые PostgreSQL regression tests: 2/2, exit 0. Барьер pg_stat_activity наблюдает
  **два** lock waits до journal. Новый синтетический SQL выполняется один раз; SQL
  failure откатывает DDL и journal; следующий migrator получает освобождённый lock.
- `pnpm check:pr`: exit 0; 578 backend tests / 40 suites и 37 web tests / 4 files,
  реальные migrations/PostgreSQL, Chromium, format/typed lint/architecture/contracts/
  OpenAPI/API generation и оба coverage guards.
- Backend 202 source: lines/statements 90.54%, branches 94.50%, functions 89.78%.
  Новый serialized-migrations.ts — 100/100/100/100; добавлен только его baseline entry.
  Существующие baseline не понижены. CLI child process coverage по-прежнему не объединён:
  migrate.ts функционально проверяется отдельными запусками, его unit lines=0 явно остаётся.
- Web baseline не менялся: lines 62.20%, statements 57.77%, branches 72.36%, functions
  52.81%. Browser coverage не объединяется с Jest/V8. Полных 100% business branches
  или всего приложения этот результат не доказывает.
- `pnpm docker:gate`: exit 0, реальный прежний Compose/API/worker/migration consumer,
  receiving/putaway/reserve/replay/DB restart и SIGTERM прошли.
- `pnpm db:migrate` с рабочей .env: exit 1; отдельная безопасная диагностика показала
  ECONNREFUSED, рабочая БД не запущена. Команда действительно выполнена; отказ окружения
  не скрыт. Повтор **того же entry point** дважды с DATABASE_URL disposable PostgreSQL
  завершился успешно, journal 33 строки; .env и dev volumes не изменялись.
- `pnpm kubernetes:gate`: полный успешный прогон initial/repeat/failure/recovery и
  PostgreSQL/PVC persistence с cleanup. Негативные Helm upgrades намеренно дают ненулевой
  код; gate проверяет эти отказы и завершает общий сценарий exit 0.

Gate использует случайный cluster name, отдельные kubeconfig/namespace/PVC/Secrets.
Root .env не читает, реальные PII и credentials не использует. Это local single-node
тест, не внешний deploy. PostgreSQL manifest — dev owner, не production DB provisioning;
backup/restore и потеря узла не испытывались. Реальный TLS/browser gateway и readiness/
active rollout/crash tests остаются WMS-303/304. Schema текущего выпуска не меняется;
совместимость будущих expand/contract migrations требует отдельного evidence.

Итоговые прогоны 2026-11-07 после review: `pnpm check:pr` и
`pnpm kubernetes:gate` — exit 0. Format check, node --check gate и git diff --check
также прошли. В gate проверены missing/invalid digest, одинаковые Secret names и
длинное release name; production Secret values не входят в rendered chart.
