# WMS-206: отгрузка и компенсационная отмена

Дата реализации — 2026-11-03. [ADR-0024](../adr/0024-shipment-compensation.md),
[подробный флоу](../flows/shipping.md). Объём ограничен принятыми B1–B4.

## Что реализовано

Shipment/lines: immutable выбранная staged партия, draft → posted/cancelled.
Partial shipment означает отдельный полностью проведённый документ на часть заказа.
Несколько draft не создают нового резерва. Posting повторно проверяет покрытие и
атомарно уменьшает onHand/reserved/active, увеличивает consumed. ShippingEffects и
unique shipmentLineId защищают основания расхода. Все effects/movements/audit/outbox,
статусы и saved HTTP result используют один context/commit.

Cancel со staged переводит заказ в cancel_pending без освобождения товара. Оператор
подтверждает полный физический возврат shipping → storage с причиной. Сервер переносит
stock, освобождает shipping и storage резерв и закрывает только неотгруженный остаток.
Если что-то shipped, status closed_mixed и shipped не обнуляется. Без shipped — cancelled.
Полная отгрузка — completed. История picked/consumed сохраняется. API GET различает
open/reservedStorage/reservedShipping/shipped/cancelled и source location allocations.

Новые shipment/return DTO, endpoints, error code SHIPMENT_NOT_FOUND, ShippingChanged v1,
registry/types/fixtures/OpenAPI; прежние события не расширены несовместимыми enum.
Миграции 0029/0030 добавляют новые таблицы, consumed, FK движения, grants и deferred
проверки. Прежние putaway/picking/reconciliation guards сохраняются; applied SQL не менялся.
Согласованный возврат требует закрытой отмены в том же commit даже при прямом вызове inventory.

## Проверки

Использованы локальные CLI установленных зависимостей. Из корня:

```sh
node apps/backend/node_modules/typescript/bin/tsc --noEmit -p apps/backend/tsconfig.json
node apps/backend/node_modules/typescript/bin/tsc -p apps/backend/tsconfig.test.json
node apps/backend/scripts/generate-event-contracts.cjs --check

```

Из apps/backend:

```sh
node node_modules/@nestjs/cli/bin/nest.js build
node scripts/generate-openapi.cjs
node node_modules/jest/bin/jest.js --runInBand
```

Первый полный успешный прогон — 528 tests, 34 suites. После него добавлены две проверки
runtime роли и физического остатка; отдельная shipping suite — 23 tests, все успешно.
Финальный полный результат фиксируется ниже после выполнения команды.

Реальные PostgreSQL migrations/locks/rollback проверяют partial/full shipment,
конкурентные draft на последние штуки, повтор того же ключа, новый ключ на posted,
draft cancellation, cancel/post race, freeze cancel_pending, mixed closure и возврат
после частичной сборки. AFTER faults на восьми таблицах posting и семи таблицах return
доказывают общий rollback и успешный повтор того же key. Reserved сверяется независимо
с SUM(active). Расходные movements сверяются с shipped; возвращённый onHand — с итогом
компенсации. Runtime warehouse_app проверен отдельно от owner harness.

При подготовке исправлены обращения к NEW.line_id для разных trigger tables и
преобразование timestamptz raw SQL → UTC ISO. Для двух конкурирующих команд одного
пользователя используются разные реальные сессии: одинаковая cookie могла бы ждать
session lock ещё до исследуемого order lock. Общий production fixture выделен для picking
и shipping вместо копирования подготовки остатков. Старые picking tests теперь учитывают
утверждённый B3 cancel_pending вместо временного отказа отмены WMS-205.

## Ограничения

Произвольные корректировки onHand/списание shortage и возврат уже shipped товара
не утверждены и не реализованы. Физическая переноска товара происходит вне БД;
после rollback требуется сверка, а не обещание автоматического физического возврата.
Нет TTL/expiration, нового consumer, UI, Kafka, Kubernetes или внешнего deployment.
Документы и возврат ограничены 1000 строками, body/envelope — 262144 UTF-8 bytes.

Рабочая локальная БД не мигрировалась: новые миграции проверяются в disposable контейнерах.
Root .env и реальные credentials не менялись. Docker image/gate не повторялись,
так как процессная упаковка не менялась. Следующий этап — WMS-207, согласно development-plan.

## Review и исправления

В текущем diff подтверждены и исправлены два замечания:

1. P2: runtime warehouse_app мог INSERT-ом дополнить уже закоммиченный shipment draft
   новым allocation. Это меняло состав относительно сохранённого ответа подготовки.
   Новая migration 0031 запрещает позднее дополнение. Штатные multi-line prepare и
   последующее posting в новой транзакции разрешены; прежние FK/quantity/limit guards сохранены.
2. P2: ShippingChanged schema принимала shipment action без shipmentId вопреки контракту.
   Conditional if/then требует ID для трёх shipment action. Для двух cancellation action
   поле не требуется. UUID format остаётся у общего свойства; strictRequired Ajv не ослаблен.
   Source schema и generated artifacts обновлены через генератор.

Первое замечание воспроизведено отдельной временной PostgreSQL-пробой под runtime ролью
с order lock и новым allocation: отказ UNIQUE не маскировал проблему. Проба удалена.
Вместо неё добавлены постоянный отрицательный тест и положительная multi-line проверка.
Пять новых contract cases покрывают producer и handler для всех action-веток.

Результаты после исправлений:

- Целевые suites: 98 tests, 2 suites, успешно.
- Полный Jest --runInBand: **538 tests, 34 suites, все успешно**.
- TypeScript typecheck, build, tests compilation, event/OpenAPI generation checks — успешно.
- Финальное форматирование, git diff --check и сверка документации выполнены.

Повторное review изменённой области не выявило новых подтверждённых замечаний.
Техническая проверка создающей транзакции использует DB xmin только внутри guard;
он не используется как долгосрочная версия, idempotency key или поле публичного API.
Production prepare не использует nested savepoints. Подробности — в shipping flow.
Applied миграции 0029/0030 не менялись. Рабочая локальная БД не мигрировалась;
0031 проверена на disposable PostgreSQL. Docker image/gate и внешний deployment не выполнялись.
