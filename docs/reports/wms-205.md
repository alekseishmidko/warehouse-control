# WMS-205: сборка заказа

Реализовано и проверено 2026-11-01. Пользователь утвердил самоназначение кладовщика:
менеджер создаёт план, исполнитель принимает его через start. [ADR-0023](../adr/0023-picking-execution.md),
[подробный флоу](../flows/picking.md), [модуль](../../apps/backend/src/modules/fulfillment/README.md).

## Что реализовано

- PickingTask/строки из текущего storage резерва. Один открытый план на заказ, до 1000 строк.
- HTTP create/start/confirm/get, server-side исполнитель, складская policy до saved replay.
- Частичная сборка, shortage/resume, нулевая нехватка без движения, запрет превышения remaining.
- Inventory переносит onHand/reserved атомарно. Источник allocation сохраняет transferred,
  новый shipping allocation связан через immutable PickingTransfer. История release не подменяется.
- Парные movements сборки имеют отдельный FK; прежний putaway FK/deferred guard сохранён.
- Audit, task/line, balances/allocations, outbox и saved response фиксируются одним commit.
- GET task показывает actual/remaining, GET order разделяет reservedStorage/reservedShipping.
- Отмена до переноса закрывает task и выпускает резерв. После переноса отмена даёт 409
  до физического возврата WMS-206. Открытый план запрещает независимый release.
- Миграции 0026/0027, runtime grants, immutable/retained и deferred guards плана и переноса.
- PickingProgressed v1: исходная schema, fixture, registry, generated TS/bundle и OpenAPI.
  OrderChanged v1 не менялся. Подписчиков нового aggregate пока нет.

Первая проверка старых suites выявила необходимость обновить точный список OpenAPI routes

DTO; исправлено явным построением plain JSON. Финальный полный прогон выполнен после исправлений.

Проверены две конкурирующие попытки start и confirm, гонка cancel/confirm с SQL barriers,
частичная сборка/shortage/resume, replay, чужой исполнитель/склад, неверная зона/quantity,

доказывают rollback вплоть до сохранения HTTP result. Проверены grants warehouse_app,
неизменяемость истории и reserved=SUM(active) каждого balance.

## Ограничения

Отгрузка, физический возврат при отмене и consumed относятся к WMS-206. Нет переназначения
исполнителя, UI, фонового expiration, новых consumers, Kafka или внешнего deployment.
Локальная рабочая БД не мигрировалась; применять 0026/0027 штатной db:migrate после build.
Root .env не менялся. Docker image/gate не повторялись: процессная упаковка не менялась.

Во время этой сессии pnpm shim попытался скачать дистрибутив из недоступной сети.
Для проверок использованы локальные Node CLI тех же установленных зависимостей.
Команды проекта и lockfile не изменены ради обхода этой проблемы.

Финальная сверка: Prettier check всего репозитория и git diff --check прошли.
Проверены относительные пути изменённых Markdown и наличие новых файлов в file-catalog.
Повторный drizzle-kit generate сообщил «No schema changes»; OpenAPI и event generation
checks прошли. Ревью проверило порядок блокировок, lineage allocations, guards обеих
пар движений, текущие права перед replay и границы WMS-206. Новых подтверждённых
замечаний в изменённой области не найдено; это не гарантия отсутствия всех ошибок.

## Исправления review, 2026-11-02

Новая migration 0028_picking_allocation_backing.sql закрывает изменение allocation без
повторной проверки его открытого плана. Constraint trigger AFTER INSERT/UPDATE читает
конечный active и remaining задач ready/in_progress/shortage на COMMIT. Самостоятельный
release без обеспечения плана откатывается; release с последующей отменой в одном context
допустим. Проверка использует текущую строку, не промежуточный NEW.active.
Индекс allocation_id обслуживает обратный поиск. Preflight под блокировками проверяет
существующие данные и останавливает migrate с 23514, не меняя историю. Applied 0026/0027
не редактировались. Комментарий reservedShipping в OrderLineDto описывает действующий
shipping резерв, а не постоянный ноль.

Пять новых постоянных PostgreSQL-тестов проверяют:

- Отказ commit при release ready/in_progress/shortage плана под warehouse_app с order lock.
  Callback завершает SQL, после чего проверяется именно deferred ошибка 23514 и полный rollback.
- Успешный release → отмена плана → COMMIT, без зависимости от порядка промежуточных записей.
- Отказ реального preflight SQL на legacy mismatch, сохранение данных без автоматической починки.
  Отключение trigger только для подготовки legacy случая в disposable admin-БД.

Выполнены TypeScript typecheck, build, компиляция tests, event generation check и
OpenAPI check через локальные Node CLI установленных зависимостей. Все 22 picking
integration tests прошли. Финальный полный Jest с --runInBand: **505 tests, 32 suites,
все успешно**, включая прежние worker child-process recovery tests. Prettier check всего
репозитория, git diff --check и проверка относительных Markdown-путей прошли.

Повторное review проверило обе стороны инварианта (изменение task/line и allocation),
конечный снимок deferred guards, runtime grants, rollback и возможность согласованной
отмены. Новых подтверждённых замечаний в исправленной области не найдено.
HTTP-контракты не менялись. Рабочая локальная БД не мигрировалась; 0028 проверена в
изолированных контейнерах. Docker image/gate и внешний deployment не выполнялись.
