# WMS-504: Kafka consumers

## Границы и контракт изменения

Пользователь поручил WMS-504.1–6. Вход — недоверенный Kafka record внутреннего publisher.
Права — mTLS topic/group ACL и PostgreSQL warehouse_app; actor задаёт application handler.
Предусловия — current migrations, retained outbox, release schemas, неизменный partition
mapping и stable inventory.putaway identity. Результат — одна задача на receipt line
без повторного stock credit, атомарные effect/audit/marker/cursor и offset после commit.
Ошибка не подтверждает message и не разрешает обгон версии. Бизнес-правила не меняются.

Открытых новых бизнес-решений нет. Выбрана строгая техническая fail-stop policy для
ошибки/gap. Автоматические retry/quarantine и полный cutover не входят в этот этап.
[ADR-0035](../adr/0035-kafka-application-consumers.md), [полный flow](../flows/kafka-consumer.md).

Дополнительные guards — kafka-consumer-config.spec.ts; kafka-consumer-adapter.spec.ts
изолирует SDK boundary для revoke после DB commit, offset int64 и heartbeat cleanup race.
Эти unit mocks не заменяют реальные PostgreSQL/broker сценарии. Прежние worker/putaway suites
проверяют сохранение local protocol и runtime-role grants после выделения общего service.
В N+1 используется technical handler для двух valid synthetic versions; текущая доменная
модель не разрешает второе receipt-posted одного receipt. Это proof transport continuity,
не новый business flow. Настоящий inventory handler проверен в duplicate/crash/rebalance cases.

## Ревью и рефактор

Проверены diff, shared transaction runner, outbox retention/FK, InventoryService/handler,
KafkaJS2.2.4 batch/heartbeat/generation behavior и существующий worker. Новая бизнес-логика
не копируется: из WorkerRepository извлечён ConsumerRepository; application service
используют оба transport. ApplicationConsumerModule отделён от scheduler/config
WorkerModule: Kafka не читает WORKER_* environment и не создаёт local polling. Общие brokers/TLS guards вынесены в infrastructure/kafka;
partition mapping — в shared/events/kafka-route, прежний publisher export сохранён.

Найдено и исправлено при реализации:

- Отзыв ownership через heartbeat первоначально не отражался в readiness до завершения
  handler. Теперь readiness немедленно теряет assignment при heartbeat error; настоящий
  rebalance test удерживает transaction barrier и проверяет rollback/successor.
- Начальный group coordinator может быть ещё не готов после запуска broker. Сетевые
  startup retries ограничены5повторами; DB callback автоматически не повторяется.
- Завершение root pnpm wrapper сигналом нельзя трактовать как exit0 Node application.
  Tests проверяют readiness/cleanup root команды и отдельно Node SIGTERM exit0.
- Смена transport без shared cursor locks дала бы окно двойного эффекта. Общая
  transaction capability проверяется реальным DB wait между local/Kafka processors.
- Проверка только eventId не защищала бы от другого payload. Exact retained-envelope
  comparison закреплено отрицательным test без handler effects.

Повторное ревью: handlers вызываются только после validation/cursor lock; errors не
подавляются; marker failure откатывает task/audit; resolveOffset и network commit
выполняются после DB commit, autoCommit отключён. Нет нового SQL schema/DDL, переписывания
applied migrations, сброса cursors или изменения рабочего `.env`/volumes.

Дополнительное ревью harness воспроизвело, что новая CONSUMER_* конфигурация не
влияла на environment fingerprint. Добавлены prefix и regression в native CLI run/ready
test: прежнее passed не принимается при смене CONSUMER_START. Heartbeat monitor также
сохраняет уже замеченную ошибку revoke, даже если concurrent cleanup успел abort-нуть timer.
Rebalance test проверяет именно StaleDeliveryError, а не случайный DB timeout.

## Запуск, evidence и ограничения

Итоговое содержимое source фиксируется ДО runner. Источник фактических итогов —
`artifacts/harness/wms-504/latest.json` и UUID logs, а не вручную дописанные результаты.
Команды из корня:

```sh
pnpm harness:plan docs/tasks/wms-504.json
pnpm harness:run docs/tasks/wms-504.json
pnpm harness:ready docs/tasks/wms-504.json
```

Обязательные gates по policy включают check:pr и backend/web image-check + Docker gate
из-за новых package scripts. Kubernetes/Kafka platform resources здесь не меняются.
Реальный broker включён в integration check:pr, local Strimzi gate не заменяет эти tests.
Отдельные реальные проверки во время разработки: backend typecheck, test:prepare и
Jest kafka-consumer/worker/putaway suites. История отказов/исправлений сохранена в этом
разделе ревью; финальный статус критериев определяется successful ready данного snapshot.

Coverage включает все собственные backend source, кроме generated. Child executable
проходит реальные IPC/Node/root command проверки, но coverage этих процессов не объединён
с Jest V8; соответствующие строки могут иметь0 в measured baseline. Baseline новых файлов
добавлен после просмотра полного отчёта52suites/673tests. KafkaMessageService и
ConsumerRepository и ApplicationConsumerService имеют100% branches; отрицательный
handler-missing test проверяет отказ без implicit no-op. Consumer entrypoint измеряется как0, module
composition подключена в parent graph и измерена как100%. Kafka adapter содержит gaps
редких SDK callbacks; startup deadline дополнительно проверен управляемым временем; они явно не считаются полным покрытием отказов. Прежние пороги не ослаблены; пустая repository subscription проверена без SQL IN().
После targeted прогона49tests baseline новых файлов уточнён: common guards/service/repository
имеют100%, Kafka adapter —98.98% lines/92.68% branches/91.66% functions. Это baseline
измерения, а не заявка на полное покрытие отказов SDK.

Ограничения: один receipt logical consumer; throughput консервативен; fail-stop блокирует
instance; revocation наблюдается с задержкой, DB+Kafka не атомарны. Full cutover/rollback,
retention replay policy, quarantine/metrics и отдельный Helm consumer deployment не
объявляются выполненными. Dev single broker не HA. Внешний deployment/сообщения не выполнялись.

Диагностический scoped coverage запуск пяти suites завершился exit1 при49passed tests:
identity controller имеет обязательный100% порог, который этот поднабор не покрывает.
Порог не менялся. Полный check:pr запускает все suites и остаётся обязательным gate.
Команда диагностики из корня:

```sh
pnpm --filter @warehouse/backend exec jest --config jest.coverage.config.cjs --runInBand --runTestsByPath .test-dist/test/integration/kafka-consumer.spec.js .test-dist/test/integration/worker.spec.js .test-dist/test/integration/putaway.spec.js .test-dist/test/unit/kafka-consumer-adapter.spec.js .test-dist/test/unit/kafka-consumer-config.spec.js
```

```sh

```

7tests passed, exit0. Эти проверки дополняют реальные integration; не заменяют их.
