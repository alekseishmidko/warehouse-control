# WMS-103: транзакции и аудит

Отчёт от 2026-10-19. Все шесть шагов выполнены; следующая задача — WMS-104.

## Что реализовано

- Shared TransactionRunner/Context, PostgreSQL adapter и Nest DI token.
- Явный borrowed context между application interfaces; scope validation,
  запрет nested run и отзыв capability после commit/rollback callback.
- Audit module с write port, validation/redaction, PostgreSQL schema и UUID/time defaults.
- Новые migrations 0001 (таблица) и 0002 (runtime grants и append-only trigger).
- Документированная политика retry: сейчас один запуск, без скрытых повторов.

Складские данные в тестовом application-сценарии заменяет существующая техническая
application_metadata: реальных receiving/inventory модулей пока нет. Writer audit
не создаёт вторую транзакцию. Старый применённый baseline 0000 не изменён.

## Проверки

`pnpm test`: 6 suites, **61 тест** (34 unit, 27 integration), оба Jest projects.
Build/компиляция tests выполнены перед прогоном. Реальная PostgreSQL 17 из Testcontainers,
те же image/digest, что Compose; изолированные БД с полным набором migrations.

Проверены совместный commit и отсутствие промежуточной видимости из другого соединения;
rollback при ошибке до audit, после audit и при invalid input; nested run,
поддельный/завершённый/чужой scope, отзыв context после rollback и повторный новый run;
конкурентные независимые root transactions; audit masking до записи в БД;
grants warehouse_app и запрет UPDATE/DELETE/TRUNCATE/отключения trigger;
защита обычного SQL владельца; Nest composition и прежние HTTP/lifecycle проверки.

40001 и 40P01 сгенерированы сервером специально для проверки отсутствия auto retry;
реальная deadlock race здесь не моделировалась. Повторная Drizzle generation:
no schema changes. SQL migration 0002 — авторская custom migration, не ручное
изменение generated snapshot или уже применённого SQL.

## Ограничения

Runtime group — NOLOGIN, внешний login и credentials требуют отдельного provisioning.
Dev Compose использует admin connection; это не production-разделение полномочий.
DBA может отключить trigger. Маскирование обеспечивается write interface,
а прямой доверенный SQL INSERT способен его обойти. Произвольный пользовательский
текст не допускается в action/entityType/reasonCode; общего реестра кодов пока нет.

Нельзя делать сетевой I/O или fire-and-forget в callback. Автоматическая retry policy,
HTTP idempotency, audit read API, складские модули и outbox ещё не реализованы.
Миграции проверены в disposable containers; dev Compose в этой задаче не мигрировался.
Admin cleanup отключает trigger только внутри disposable test БД и включает обратно.

Инструкция: [transactions](../transactions.md),
[audit module](../../apps/backend/src/modules/audit/README.md).

## Последующая организация кода

По запросу пользователя audit переведён на обычный NestJS AuditService → AuditRepository.
Прежние AuditWriter/AUDIT_WRITER/PostgresAuditWriter удалены. Типы/helpers и schema
перенесены в корень audit-модуля. Транзакции, SQL schema и права не менялись;
исторические результаты WMS-103 выше относятся к исходной реализации.
Основание: [ADR-0009](../adr/0009-nest-service-repository-default.md).

Проверка после перехода: pnpm test — 7 suites, 63 tests (36 unit, 27 integration),
включая отдельные проверки AuditService. Drizzle generation: no schema changes.

Дополнительно файлы AuditService/AuditRepository и внутренних DTO сгруппированы
в services/, repositories/ и dto/. README audit описывает sequence diagram,
движение input/prepared DTO/SQL/result, ошибки и commit/rollback с примерами.
Поведение и схема БД при этом не меняются.
