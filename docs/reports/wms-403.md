# WMS-403: нагрузочные сценарии и baseline

Числа и проверки ниже относятся к приёмке WMS-403 от 2026-11-12.
Generated baseline обновляется успешной командой `pnpm load:baseline`;
повтор после исправлений описан в [ревью 2026-11-13](review-fixes-2026-11-13.md).

## Изменение и границы

Оператор запускает отдельные `load:throughput`, `load:sku`, `load:backlog` или общий
`load:baseline`. Driver создаёт собственные Compose projects, новую PostgreSQL БД,
синтетические warehouses/SKU/users, настоящие sessions и warehouse grants.
Произвольный URL/DSN не принимается, remote Docker endpoint отклоняется до запуска.
Рабочие `.env` и volumes не используются. API/worker используют один backend image
с разными entrypoints. Бизнес-код, migrations и contracts приложения не менялись.

Успешный результат — измеренный профиль и независимая SQL-сверка committed фактов.
Ошибка HTTP, dropped iteration, нарушение ledger или отказ cleanup не становятся
accepted baseline. Три штатных `INSUFFICIENT_STOCK` явно учитываются как бизнес-отказ.
Новый key после неизвестного результата не используется. Известный успешный post
отдельно replay-ится тем же actor/key/body, без новых эффектов.

Подробный владелец последовательности, входа, SQL, Mermaid, ошибок и cleanup —
[load flow](../flows/load-testing.md). [Команды и файлы](../../load/README.md),
[драйвер](../../scripts/load/README.md). Открытых бизнес-решений нет; SLO и recovery
остаются WMS-404. Новое архитектурное решение приложения не вводилось, ADR не менялись.

## Измерения итогового baseline

HTTP durations приведены в ms. В throughput/backlog одна бизнес-итерация включает
create и post; в SKU — один reserve. Setup/control requests в k6 не входят.

| -------------- | -----------: | ----: | ----: | ----: | ----------: | -------------------------------- |
| throughput     |          402 |  9.49 | 23.65 | 56.25 |          0% | 201 posted receipts              |
| one SKU        |            4 | 65.86 | 66.96 | 67.08 |          0% | 1 success / 3 INSUFFICIENT_STOCK |
| stopped worker |          200 | 22.77 | 51.19 | 66.76 |          0% | 100 posted receipts              |

Throughput: 20.08 HTTP req/s,
10.04 receipts/s;
receipt create+post HTTP duration p95 46.06 ms.
Dropped iterations — 0. Пик backlog 2, oldest age
0.194 s, max sampled lock waiters 0.

SKU barrier наблюдал 4 одновременных DB waiters;
hold 409.01 ms включает старт k6 и ожидание контрольного условия.
Искусственный barrier входит в latency. По четырём samples нельзя оценить устойчивый
population p99. Периодический sampler 100 ms увидел максимум
1 waiters; он может полностью пропустить короткое ожидание.
После shutdown PostgreSQL зафиксировал
3 rollback от отказавших резервов;
периодические stats публикуются с задержкой. Deadlocks во всех сценариях — 0.

Backlog вырос до 100 pending при 0 completed и 0 task/marker effects.
После запуска worker очередь разобрана за 5.693 s,
17.57 events/s, включая startup/readiness/polling.
Максимальный возраст незавершённой delivery 5.937 s.
`samples` сохраняет рост и drain curve, а не только конечный ноль.
Это скорость конечного пакета из 100 событий, не предел постоянного consumer rate.

## Ревью, исправления и повторное ревью

Проверены новые файлы, итоговый diff и связанные paths: seed/identity/receiving,
fulfillment reservations, stock ledger, transactional outbox/worker и Docker transport.
Бизнес-операции используют владельцев приложения; SQL harness только читает и
держит контрольный lock. Production SQL/migrations не переписаны.

| Finding                                                              | Воспроизведение / исправление                                                                                                                                                                                                                  | Regression evidence                                                                                                                      |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| P2 / L-01: cleanup маскировал первичную фазу ошибки                  | Первый unpaced прогон остановился по backlog ceiling, но показывал `cleanup`; `cleanupResources` сохраняет primary error и отдельно имена отказов cleanup, пытается удалить все свои ресурсы                                                   | `cleanup retains primary failure and attempts all resources including secret deletion`                                                   |
| P2 / L-02: точный count отвергал допустимую границу arrival executor | Наблюдались 501 успешная пара при target 500, без dropped/errors; проверка использует planned..planned+1, completed iterations, 2 HTTP на пару и posted counter. Недобор/лишние ticks вне границы всё ещё запрещены                            | `arrival-rate boundary tick is valid but incomplete receipt pairs and errors are rejected`                                               |
| P2 / L-03: receiver как PID 1 не завершался по SIGTERM               | Реальный cleanup не удалил monitoring project; отдельный container stop до фикса дал 137 без OOM. `startReceiver` закрывает listener, ждёт requests до 2 s и закрывает зависшие соединения; Compose grace 5 s. После фикса Docker PID 1 exit 0 | `receiver drains SIGTERM and bounds an unfinished HTTP body`, реальный Docker stop до/после и повтор root load/observability entrypoints |

Рефактор: конфигурация, dataset, sampling, read-only сверка и проверка k6/evidence
выделены в отдельные модули. Docker transport переиспользован через guarded import,
без второго implementation shell/timeouts. Guard отбрасывает private fields и
известные capabilities в public evidence; bootstrap/login capabilities не печатаются.
Native child-process test фактически проверяет отказ remote endpoint без вывода
синтетического пароля. Это проверка безопасности, не обнаруженная утечка.

Повторное ревью исправлений не выявило других блокирующих дефектов в затронутых
сценариях. Реальные отдельные команды и общий baseline повторены после исправлений.
Прежние `docker:gate` и `observability:gate` проверяют guarded import и старые entrypoints.
Полный результат PR/Docker gates приведён ниже; их зелёный статус не заменяет это ревью.

## Предварительная калибровка и ограничения

Unpaced receiving увеличивал outbox выше ceiling 1000; защитный отказ не был выдан
за accepted baseline. Отдельный probe 25 receipts/s сохранил 352 полные приёмки,
0 HTTP errors, 149 dropped iterations, HTTP p99 около 975.60 ms, p95 205.66 ms.
Point-in-time committed facts имели нулевые ledger/effect errors; полный post-load
accepted gate у probe не пройден. [Сохранённый failed evidence](wms-403-probe-25rps.json).
Отсутствующие данные раннего unpaced прогона не восстановлены и не придуманы.

Системный power log подтвердил Sleep/DarkWake/Wake и многочасовые паузы машины.
Один повтор остановился ещё в dataset без бизнес-записей; он не является benchmark.
Итоговый общий baseline и Docker проверки выполняются под `caffeinate -i` с временным запретом
idle sleep. Постоянные настройки питания не менялись.

Reference rate 10/s выбран для начального воспроизводимого сравнения. Error,
dropped, p99 safety и бизнес-проверки не ослаблялись. Один успешный trial 25/s и
другой trial с dropped показывают вариативность этой машины; это не доказанная
граница capacity и не установленная причина CPU/DB bottleneck. Предварительные
прогоны делались во время доработки harness; для точного сравнения используется
итоговый baseline с окончательным hash inputs. Целевая production нагрузка/SLO не
заданы. Для нового эксперимента менять бюджет в отдельном checkout и фиксировать
новую конфигурацию/evidence, не переписывать этот результат.

Измерен receiving API и один hot stock key. Модель host SSD и fsync latency отдельно не измерялись. Не измерены все API routes, TLS/gateway,
UI rendering, внешний network, большие каталоги, длительный soak или saturation.
CPU VM общий с monitoring/фоновыми процессами; host не был эксклюзивным benchmark
сервером. Сам SQL sampler вносит overhead. Single PostgreSQL — dev, не HA.
Нет нового crash/lease/DB-outage load drill: WMS-304 evidence не заменяется,
recovery/SLO остаются WMS-404. Driver SIGKILL/потеря daemon не гарантируют finally;
manual scoped cleanup описан в flow. Pulled images/build cache остаются на машине.
