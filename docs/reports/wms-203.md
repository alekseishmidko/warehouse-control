# WMS-203: размещение и перемещения

Реализация 2026-10-29, решение [ADR-0021](../adr/0021-putaway-execution.md),
исполнение/SQL/ошибки/гонки — [подробный flow](../flows/putaway-execution.md).
Модульный монолит и отдельный worker сохранены, внешнего deployment нет.

## Результат для менеджера

PutawayTask исполняется целиком из receiving в storage того же склада. Оператор выбирает
назначение; source/product/quantity определяет task. После переноса 10: source=0, target=10,
общий stock=10, task completed. Повтор исходного key не переносит снова; новый key получает 409.
Переносится только свободный stock, reserved в source не изменяется. Произвольный transfer,
межскладские переносы, partial/cancel и перенос активного allocation не реализованы.

## Реализация

- InventoryService → private PutawayExecutionService с caller transaction context.
- Task FOR UPDATE, создание нулевых balances и FOR UPDATE в одинаковом порядке ключей,
  проверка onHand-reserved/capacity, debit/credit без lost update/overflow.
- Две immutable movement legs с positive int4, transferId=taskId, отдельными unique operationId,
  один completion audit, PutawayCompleted event, task state и saved HTTP result — один commit.
- Источник/audit создания неизменны. Новые nullable completion columns и transferId, CHECK/FK/
  UNIQUE, state guard и deferred pair constraint; UPDATE column grants warehouse_app.
- InventoryHttpModule API-only, GET task/read и POST execute/putaway; production session/CSRF/ACL
  проверяется до dedup replay. Worker InventoryModule не требует человеческой AUTH policy.
- inventory.putaway-completed v1: исходная JSON Schema/example, registry/KnownEvent, generated
  TS/schema bundle и producer/handler validation. Aggregate putaway-task, causation исходного event.
  Новых consumers/deliveries пока нет, событие retained; receipt stream/subscription сохранены.
- OpenAPI regenerated из production controller/DTO, новые безопасные error codes и audit fields.

## Ограничения

Нет UI/scanner/доказательства физического перемещения, общего transfer API, partial/cancel,
работающих allocations или subscribers нового completion event. Новый consumer требует
migration/replay/start-position плана, retention по-прежнему запрещает удалять историю.
DBA может обойти guards, ровно один физический внешний эффект не обещается. Изменения
БД/события/HTTP result атомарны в PostgreSQL; доставки наружу здесь нет.
Auth требует прежних явных AUTH_ORIGIN и обоих сроков сессии, defaults не добавлялись.
