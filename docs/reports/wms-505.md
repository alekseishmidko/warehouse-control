# WMS-505: ошибки Kafka и восстановление

## Изменение и доверие к входу

Запрос пользователя: WMS-505.1–5. Согласованы полный decoded raw record и узкое dev-исключение
ADR-0036. Вход Kafka недоверенный: body/key/headers могут содержать произвольные данные.
Хранение только AES-256-GCM, source identity immutable. Права recovery — local opt-in
и DB admin role, operator UUID не заменяет права. Для warehouse effects используется
прежний application handler с прежними markers/cursor. HTTP/stock правила не меняются.

Успех — recovery original Kafka position с прежним eventId и одним business effect.
Quarantine не является applied fact и не разрешает обгон. Вне задачи — production key
custody/deployment, полный cutover WMS-506, восстановление удалённой Kafka history.
Новая migration0034 additive; custom SQL является владельцем таблицы вне ORM schema.

## Ревью → исправления → повторное ревью

Проверены application handler, source contracts, DB transaction runner, consumer SDK
ownership/offset flow, admin-role guards, metrics labels и data retention. Политика
ADR-0036 не заменяет реализацию: новый partition protocol описан ADR-0037.

Исправлены найденные при реализации случаи:

- Root pnpm wrapper exit не доказывает завершение Node consumer. Tests ждут реальный
  leave group и недоступность probes, не добавляют случайный sleep.
- Export через macOS /var symlink корректно запрещён. Test/operator использует canonical
  parent, leaf создаётся O_EXCL/O_NOFOLLOW и0600. Правила не ослаблены ради test.
- Отключение crypto profile не должно обходить существующий durable gate. Проверка
  gate/resolution независима от enable записи новых encrypted failures.
- При Kafka start после poison pause должен seek-нуть original blocked offset, а не
  текущий поздний record. Это закреплено restart с реально изменённым group offset.
- Pause timers старой assignment не могут seek-нуть отозванную partition; epoch проверяется
  после async probe, group join снимает timers и заново допускает только DB-checked records.
- Воспроизведены до исправления два regression race: revoke во время SQL resolution
  ошибочно коммитил effect; concurrent cleanup/export возвращал undefined ciphertext
  после authorization audit. Добавлены завершающая ownership check и missing-row guard
  до audit; реальный PostgreSQL/barriers tests подтверждают rollback и корректный отказ.
- Runtime SELECT ограничен metadata columns, ciphertext доступен только admin role.
  Export snapshot содержит source address, authenticated AAD не зависит от object key order.
- Broker metrics не выполняют I/O под DB locks или в scrape. Используется один cached
  probe с bounded SDK retries. Durable age включает retained events без marker и failures.

Общие правила не копируются в новый складской handler. QuarantineRepository остаётся
private, AuditService используется публично. SQL ошибки не подавляются в business
transaction; crypto/fs выполняются вне callback. Failure storage error не разрешает ack.

Дополнительно выделен kafka-lag.metrics.ts: Kafka adapter отвечает за records/ownership,
observer — за cached network metrics. Это устранило смешение двух lifecycle задач.
Весь целевой scope после исправлений:45tests passed. Диагностическое V8 измерение
использует обычный Jest config и collectCoverageFrom только Kafka capability; оно
не отключает thresholds обязательного полного check:pr и не выдаётся за backend coverage.
Новые baseline entries отражают это измерение; существующие thresholds не снижены.
Kafka adapter100% lines/branches, crypto100% lines/92.85% branches, repository98.59% lines/98.24% branches,
recovery service95.1% lines/91.07% branches. CLI и type-only DTO имеют0 measured runtime
lines: child execution и erased types не объединяются с parent Jest V8. Редкие filesystem
ошибки и часть defensive input branches остаются gaps, не скрываются за общим процентом.

Последний review дополнительно воспроизвёл permanent→retry при late transient failure:
исходный test на runtime DB role получил retry/TRANSIENT_FAILURE вместо закрытой quarantine.
Исправлено sticky state/reason и SQL transition guard; UPDATE retry_base отозван у runtime.
Воспроизводимый test проверяет отсутствие обхода через прямой runtime UPDATE/resolve.

Один полный run обнаружил cold startup отказ первого Kafka consumer до handler. Исходный
SDK reason не сохранился: raw SDK logging выключен. Это не объявляется доказанным
GROUP_LOAD_IN_PROGRESS. Добавлены read-only coordinator readiness и allowlisted crash
reason; unit tests подтверждают transient readiness wait и отсутствие retry auth errors.
Итоговый full run должен подтвердить работу на настоящем cold broker.

Новые root команды `pnpm kafka:admin ...` и `pnpm consumer` проверяются реальными child

Узкий testNamePattern505 использовался для диагностики, не заменяет итоговый полный run.

Coverage включает все собственные backend source; child CLI/bootstrap coverage отдельно
не объединяется с Jest. Metadata-only DTO может иметь0 runtime lines. Пороги прежних
файлов не должны снижаться без обоснованного review; новые baseline требуют фактического
измерения. Gaps rare filesystem/SDK faults отражаются в measured отчёте, не объявляются
100% business coverage. Полный gate не является production recovery drill.

Structured failure logs выводятся только после failure commit: quarantineId + partition
позволяют получить safe inspect без SQL-поиска UUID в свободном тексте. Loki labels остаются
прежними bounded service/environment/process/module. Новый Pino regression test проверяет
валидацию UUID/partition и отсутствие raw/ciphertext в log fields.

Cold/readiness/sticky regression scope завершился47passed/1failed: key mode0700
не соответствовал заявленным0400/0600. Валидатор исправлен, отдельный crypto scope4tests
passed; остальные47tests были успешны. Итоговый полный run обязан выполнить их вместе.
Новые baseline entries уточнены по фактическим per-file V8 measurements; пороги
старых файлов сохранены. Рабочий key file не создавался и .env не менялась.

Фактические source команда/окружение: Node24.22.3, pnpm10.18.3, Docker disposable
PostgreSQL17 и pinned Kafka fixture. Endpoint/dashboard metrics не объявляются
проверенными во внешнем Prometheus/Grafana: проверены настоящий exporter output и broker
lag probe. Production key custody и HA не входят в согласованную dev-политику.
