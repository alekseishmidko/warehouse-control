# План разработки Warehouse Controller

Документ превращает [roadmap](roadmap.md) в последовательный backlog для разработчика,
менеджера и агента: задачи, зависимости, проверяемый результат и демонстрация этапа.
Это план, не отчёт о выполнении. Все задачи ниже имеют статус «запланировано».
Реализован только каркас NestJS; актуальный статус — в [карте документации](README.md).

## Как работать с планом

Задачи обозначены `WMS-<этап><номер>`; один идентификатор сохраняется при переносе
в issue tracker. Каждая строка — основа задачи, а не требование одного большого PR.
Крупную задачу разбивать на проверяемые изменения, сохраняя ссылку на родителя.
Внутри этапа зависимости указаны явно, следующий этап начинается после его gate.
Внешнее развёртывание и публикация образов требуют отдельной задачи с указанным окружением.

Сроки не назначены: сначала измерим скорость на первом сценарии. После его демонстрации
можно оценивать следующие этапы, учитывая доступное время и ресурсы локального стенда.
Согласование открытого бизнес-правила выполняется до зависимой реализации;
независимые задачи можно продолжать.

## Контрольные результаты для менеджера

| Этап | Что можно показать | Условие перехода |
|---|---|---|
| 1 | Принять товар и получить задание размещения после рестарта worker | Нет потери операции и повторного начисления |
| 2 | Пройти складской путь от приёмки до отгрузки через UI | Права, остатки и компенсации проверены |
| 3 | Запустить тот же сценарий в Kubernetes | Рестарт и rollout не теряют данные |
| 4 | Найти причину задержки и измерить работу под нагрузкой | Есть dashboards, alerts и baseline |
| 5 | Повторить сценарий через Kafka, включая недоступность broker | Cutover и повторная доставка проверены |
| 6 | Выпустить проверенный образ через GitOps и восстановиться после ошибки | Поставка и восстановление воспроизводимы |

## Общая готовность каждой задачи

- Выполнен сценарий и его отрицательные случаи; проверки соответствуют изменению.
- Нет прямых записей в чужие таблицы и повторного выполнения бизнес-эффектов.
- Проведён поиск существующей логики; shared выделен по [правилам](shared.md).
- Обновлены README модуля, комментарии файлов, [каталог](file-catalog.md),
  контракты, примеры и бизнес-описание при изменении поведения.
- Миграции и конфигурация описаны; секреты и реальные данные не добавлены.
- Пройдены существующие build/typecheck и необходимые новые проверки.
- В результате задачи указаны выполненные проверки, ограничения и фактический статус.

Автоматические gates вводятся постепенно; запланированная проверка не считается работающей.
Тесты outbox и конкуренции выполняются на реальной PostgreSQL, не только на моках.

## Этап 1. Приёмка, outbox и Docker

Начальный объём ограничен одним сквозным сценарием. Минимальные справочники и
пользовательские fixtures используются в изолированном dev/test до готовности identity.
Тестовый actor берётся из явно включённого server-side dev context, не из body запроса;
режим должен отказывать при попытке включения вне dev/test.

| ID | Задача и зависимости | Результат и критерий приёмки |
|---|---|---|
| WMS-101 | PostgreSQL, Compose, конфигурация, Drizzle | Пустая БД поднимается по инструкции; конфигурация валидируется при старте; есть первая миграция и безопасный `.env.example` |
| WMS-102 | Jest/Supertest/Testcontainers; после 101 | Изолированный integration harness применяет миграции, очищает fixtures; тест rollback выполняется на PostgreSQL |
| WMS-103 | Transaction context и аудит; после 102 | Application-сценарий передаёт одну транзакцию между модулями; audit и данные откатываются вместе; адаптеры не скрывают отдельный commit |
| WMS-104 | Минимальные catalog/warehouses/inventory; после 103 | Есть SKU, склад, ячейки приёмки/хранения; unique/check/FK constraints; конфликт создания нового balance обработан |
| WMS-105 | Инструменты контрактов; после 102 | JSON Schema runtime validation, проверка fixtures с formats, генерация типов; неизвестные дополнительные поля допускаются, неверное quantity отклоняется |
| WMS-106 | Outbox writer и migrations; после 103, 105 | Событие, delivery и stream создаются атомарно; eventId и aggregate sequence уникальны; rollback не оставляет события |
| WMS-107 | HTTP-основа команд; после 103 | Problem responses, валидация DTO, correlationId, OpenAPI и Idempotency-Key; параллельный повтор получает прежний результат, другой payload с тем же ключом — 409 |
| WMS-108 | Создание и проведение приёмки; после 104, 106, 107 | Receipt posted, остаток, movement, audit и event фиксируются вместе; повторное проведение не начисляет товар снова |
| WMS-109 | Durable worker; после 106 | Claim/lease/token, cursors, retries/dead и shutdown по протоколу outbox; ошибки одной версии блокируют её stream, другие агрегаты продолжаются |
| WMS-110 | Задание размещения; после 108, 109 | Handler создаёт одно задание через inventory; effect + processed marker + cursor + delivery completion атомарны; товар не начисляется повторно |
| WMS-111 | Диагностика и восстановление; после 109, 110 | Логи с eventId/correlationId; управляемые inspect/retry команды с журналом вмешательства; dead заметен оператору; runbook содержит реально проверенные команды |
| WMS-112 | Образ API/worker и демонстрация; после 108–111 | Один multi-stage non-root image, разные entrypoints, Compose; SIGTERM и рестарт проверены, команды запуска воспроизводимы |

Протокол реализации: [outbox](outbox.md), пример события: [contracts](contracts/README.md).
Для управления retry в dev допускается локальная административная команда с явной
идентификацией оператора; внешний административный endpoint до identity не открываем.

### Проверки gate 1

Откат после изменения остатка не оставляет receipt posting, движения, audit или outbox.
Два запроса проведения не удваивают количество. Два workers не удваивают задание.
Убийство worker после claim и во время обработки допускает восстановление.
Падение до/после handler commit не оставляет частичного эффекта.
Порядок версий одного агрегата сохраняется; другой агрегат обрабатывается параллельно.
Неизвестная версия отправляется в диагностику, а не считается успешно обработанной.
Оператор воспроизводит retry по [runbook](runbooks/event-recovery.md).

Демонстрация: принять 10 штук, остановить worker, увидеть ожидающее событие,
запустить worker и получить ровно одно задание размещения.

## Этап 2. Складской процесс и интерфейс

| ID | Задача и зависимости | Результат и критерий приёмки |
|---|---|---|
| WMS-201 | Уточнение правил | До fulfillment согласованы частичная сборка/отгрузка, отмена после сборки, срок резерва, SQL-тип и предел количества, лимиты размера документов/событий |
| WMS-202 | Identity и матрица доступа; после 201 для зависимых правил | Выбран механизм auth; роли и доступ к складам проверяются сервером; истечение/отзыв сессии и 401/403 проверены; dev actor не обходит production auth |
| WMS-203 | Размещение и перемещение; после 202 | Парные движения и балансы атомарны; общее количество сохраняется; повтор задания не переносит товар второй раз |
| WMS-204 | Заказ и резерв; после 201–203 | Детерминированный выбор остатков, allocations и блокировки; два заказа конкурируют за последнюю штуку, успешно резервирует только один |
| WMS-205 | Сборка; после 204 | Фактическое количество и allocation переносятся в отгрузку вместе; обработаны нехватка и частичная сборка по утверждённым правилам |
| WMS-206 | Отгрузка и компенсации; после 205 | Одновременное уменьшение onHand/reserved, запрет повторного списания; отмена и корректировки сохраняют историю и проверяют права |
| WMS-207 | Read API и история; после 203–206 | Остатки, доступность, движения, состояния документов и audit доступны с фильтрами, стабильной pagination и проверкой доступа |
| WMS-208 | Web и generated api-client; после 202 и стабильных API | UI для справочников, приёмки, размещения, заказа, сборки, отгрузки и истории; DTO не копируются вручную; ошибки и ожидание обработки видны пользователю |

Web можно вводить по мере готовности API, не ожидая завершения всех экранов.
Бизнес-правила остаются на сервере. В UI учитывать повтор отправки и неопределённый
результат при сетевом timeout, не считать timeout доказательством rollback.

Gate 2: согласованный путь «10 принято → 10 размещено → 3 зарезервировано →
3 собрано → 3 отгружено → осталось 7» воспроизводится через UI.
Проверены отказ по правам, отмены, повтор команды и частичные операции.
Остатки сверяются с движениями, reserved — с активными allocations.

## Этап 5. Kafka без удаления outbox

| ID | Задача и зависимости | Результат и критерий приёмки |
|---|---|---|
| WMS-501 | Kafka/Strimzi и topology | Поднимается dev-кластер, определены topics/keys/groups и retention; все версии агрегата имеют один key и topic |
| WMS-502 | Registry и AsyncAPI; после 501 | Проверена совместимость JSON Schema dialect и выбран Registry; контракты публикуются из Git; breaking changes отклоняются проверкой |
| WMS-503 | Singleton publisher; после 501, 502 | Pending deliveries публикуются с прежним eventId; completion только после broker ack; потеря ack допускает дубликат, а не потерю |
| WMS-504 | Consumers; после 503 | Stable consumer names, schema validation, DB effect + marker/cursor атомарны; offset после commit; обработаны rebalance, дубликат и разрыв последовательности |
| WMS-505 | Retry/quarantine и диагностика; после 504 | Ошибочный event не пропускается молча; определено влияние на stream/partition; видны lag и ошибки; ручной retry сохраняет eventId |
| WMS-506 | Репетиция cutover; после 505 | Пройдены backup, остановка записи, boundary, остановка старого worker, перенос незавершённых delivery, проверка и открытие записи по runbook |

До cutover решить и проверить важный случай: после локального завершения версий
1…N новый Kafka consumer получает N+1. Его cursor должен продолжаться от сохранённой
позиции, а не ожидать версию 1. Backlog и недоставленные события сверяются отдельно
для каждого logical consumer; смена транспорта не сбрасывает markers.

Gate 5: тот же бизнес-сценарий работает через Kafka; проверены broker outage,
lost ack, падение consumer после DB commit до offset commit и rebalance.
Ни локальный, ни Kafka путь не создают двойной эффект при переключении.
План возврата учитывает новые эффекты и новый boundary.
Несколько publisher replicas и fencing — отдельное исследование после этого gate;
одна replica в Kubernetes сама по себе не защищает от перекрытия старого и нового pod:
на первом этапе запуск publisher предусматривает исключение такого перекрытия.

## Следующая задача для агента

Начать только с **WMS-101**: прочитать AGENTS, архитектуру, ADR, стандарты
документации и shared. Проверить доступность Docker и локального окружения.
Добавить PostgreSQL/Compose, Drizzle-конфигурацию, первую миграцию и валидацию
настроек. Документировать запуск, параметры, файлы и фактические проверки.
Не добавлять пока Kafka, весь домен или пустой общий framework.
Если Docker недоступен, явно зафиксировать непроверенную часть и продолжить
независимую подготовку; не объявлять миграцию проверенной на реальной БД.
