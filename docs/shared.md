# DRY и shared-слой

Правила устраняют повтор общей логики, сохраняя бизнес-правила у владельцев модулей.

| Логика | Размещение |
|---|---|
| Общая внутри одного модуля | Внутри этого модуля |
| Общая техническая логика backend | `apps/backend/src/shared/<capability>/` |
| Подключения БД/Kafka/OTel и адаптеры I/O | `apps/backend/src/infrastructure/` |
| Общий код нескольких приложений | `packages/<capability>/` при реальных потребителях |
| Правила остатков и резервов | inventory, вызов через экспортируемый сервис |
| Типы API и событий | Генерация из контрактов |

Примеры shared: Clock/IdGenerator ports, формат технических ошибок, pagination,
общая retry policy с чёткими гарантиями. DB-реализация Clock размещается в infrastructure.
Retry транзакции и внешнего I/O нельзя объединять только из-за похожего цикла.

Modules и infrastructure могут зависеть от shared. Shared не импортирует
бизнес-модули, infrastructure, контроллеры или конкретные ORM-сущности.
Nest-зависимые технические адаптеры размещаются в infrastructure.
Frontend не импортирует backend shared напрямую.

## Порядок работы

1. Перед написанием функции найти существующую реализацию через `rg`.
2. Переиспользовать существующий контракт, если совпадают смысл, ошибки и эффекты.
3. При смысловом дублировании выделить общий компонент и обновить потребителей.
4. Если повторяется бизнес-правило — обращаться к владельцу домена.
5. Если сходство только синтаксическое — не связывать независимые правила.
6. Документировать новую абстракцию и проверить всех её потребителей.

Не создавать общие свалки utils/helpers, universal base service, generic repository
для сокрытия разных транзакций или абстракции с настройкой на каждый частный случай.
Одинаковые числа не обязательно означают одну общую константу.
Shared создаётся при появлении реального кода. WMS-103 добавляет первую capability:
transactions — opaque context и runner port без ORM/транспорта.
Каждая capability имеет README, file-level docs и проверки существенного поведения.
