# WMS-201: проект контрактов исполнения заказа

**Не опубликовано и не реализовано. Бизнес-политики B1–B4 утверждены 2026-10-29.**
Здесь описаны предметные границы будущих команд, не OpenAPI routes или готовые DTO/JSON Schema.
[Правила](../fulfillment-rules.md) владеют состояниями, [flow](../flows/fulfillment.md)
— последовательностями и AC. Существующие receiving endpoints/ReceivingPosted v1
не меняются; generator не должен добавлять эти проектные операции в OpenAPI.

## Логические команды и результат

| Действие                       | Недоверенный ввод будущего DTO                            | Обязательная серверная проверка / эффект                                                                                |
| ------------------------------ | --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| Создать/подтвердить заказ      | warehouseId, уникальные productId/quantity                | Справочники и ACL, лимиты; назначить IDs, зафиксировать состав. Отсутствие stock не создаёт отрицательный резерв        |
| Резервировать                  | orderId/lineId, фактические quantities                    | Статус/order remainder, разрешённые storage balances, available под locks; inventory владеет allocations                |
| Подтвердить сборку             | taskId, actualQuantity, source/target при необходимости   | Активное обеспечение своего заказа и shipping своего склада; перенос обеих сторон и allocation атомарно                 |
| Зарегистрировать нехватку      | taskId, remaining expectation, технический reasonCode     | B2: не корректировать stock автоматически, не создавать movement quantity=0; расхождение разбирается отдельно           |
| Создать/провести shipment      | orderId, строки/количества фактической staged партии      | Покрытие shipping allocations и остатка заказа, отсутствие cancel_pending; posted неизменяем                            |
| Отменить остаток заказа        | orderId, reasonCode                                       | B3: release storage либо cancel_pending; не отменять shipped и не стирать историю                                       |
| Подтвердить возврат при отмене | orderId, полный вектор source/target/quantity, reasonCode | B3: факт физического действия заявляет оператор, целевые storage в том же складе; перенос + release + закрытие атомарны |

Actor, ACL, status, new balances, consumed/released, eventId/aggregateVersion и auditId
не задаются пользовательским body. Разные команды имеют стабильные operation names,
которые будут утверждены при API-дизайне. Для всех команд действует существующий
scope Idempotency-Key, hash нормализованного ввода, безопасные problem responses и
проверка доступа на каждой попытке до dedup; конкретные новые code/DTO пока не добавлены.

Read result должен различать ordered/open/reservedStorage/reservedShipping/shipped/
cancelled и состояния документов: одна строка status не объясняет частичное исполнение.
HTTP saved response остаётся snapshot первоначального commit, GET — текущее состояние.
Новое имя поля или состояние в будущих контрактах не добавляется в существующую v1
приёмки ради переиспользования DTO.

B1 разрешает частичные операции с открытым остатком заказа; B2 — подтверждение найденного
без автоматического списания недостачи; B3 — release до сборки и физический возврат
собранного перед закрытием отмены; B4 исключает автоматический expiration. Согласование
этих политик не утверждает дополнительные меры блокировки позиции, точный DTO/статусы
и новые лимиты: их необходимо завершить до реализации соответствующих операций.
Нет expiresAt/TTL/expiration endpoint/job; резерв не освобождается от одного течения времени.
Гонки явных release/cancel с pick/ship остаются обязательными проверками.

## Лимиты: что принято, что предлагается

| Параметр                  | Этап 1, действующее ограничение     | Предложение для новых контрактов, не утверждённое WMS-201                                                                  |
| ------------------------- | ----------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| Фактическое quantity      | integer 1..2147483647, без coercion | Сохранить ту же единицу/диапазон; ноль только у счётчика или отдельного сообщения о нехватке без movement                  |
| Balance/active counters   | 0..2147483647, reserved<=onHand     | Сохранить для каждой позиции/строки; проверять итог назначения при transfer                                                |
| Строки receiving          | 1..1000, productId уникален         | Order/shipment тоже 1..1000 разных productId; limit новых DTO утвердить до записи данных                                   |
| Сообщение ReceivingPosted | <=262144 UTF-8 bytes всего envelope | Сохранить ceiling для каждого нового типа события; фактическую максимальную форму проверить schema/fixtures до регистрации |
| HTTP JSON body            | 256*1024 bytes                      | Не увеличивать молча; body limit и envelope limit проверять независимо                                                     |
| Версия события            | 1..Number.MAX_SAFE_INTEGER          | Сохранить; версии aggregate/order/shipment должны иметь определённого владельца перед первым append                        |

1000 строк не гарантируют попадания в bytes: IDs, строки и envelope тоже занимают место.
Если новый payload не помещается, нельзя молча обрезать строки, автоматически разбить
один факт на несогласованные версии или увеличить bytes существующей schema. Перед
публикацией выбирается меньший документ/иной контракт; после публикации breaking change
требует major-версии, плана миграции consumers и новых fixtures/generation diff.

Суммы многих balances склада нельзя возвращать как безусловно точный JS number без
отдельного ограничения/формата. Per-balance int4 не ограничивает сумму всего склада.
Новые SQL виды движений/reservations/states требуют новых миграций: текущее receipt-only
CHECK и UNIQUE operationId нельзя обходить прямыми записями чужого repository.

## События и доставка

Названия/формы order/reservation/picking/shipment событий пока **не зарегистрированы**.
До реализации каждого producer: исходная JSON Schema 2020-12, описание бизнес-факта и
агрегата/версий, fixtures, generated types/bundle, registry, consumers и проверка bytes.
Новый aggregateType/destination требует миграций и плана старта/replay: текущие SQL CHECK
outbox рассчитаны на receipt/inventory.putaway, редактирования массива подписчиков мало.

В одном commit фиксируются эффект, audit, движения и факт; handler не повторяет уже
сделанное начисление/перемещение. Разные order/shipment агрегаты не получают глобального
порядка от outbox. Новые consumers обязаны проверять ссылки/идемпотентность, не предполагать
порядок между агрегатами и не обещать атомарность PostgreSQL+Kafka.

## Что проверять до объявления готовности API

- Сохранены принятые B1–B4; до первой записи отдельно определены лимиты новых документов
  и дополнительные проектные детали, нет противоречий с таблицами переходов.
- DTO/runtime/SQL/schema/bytes имеют один диапазон, граничные и неизвестные поля покрыты fixtures.
- AC-01–AC-06 проверены реальной PostgreSQL integration suite, включая rollback/idempotency/races.
- OpenAPI отражает только реально подключённые endpoints и documented error codes.
- Новые migration files, контрактные версии и generation diff согласованы с потребителями.

Текущие source schemas, OpenAPI, registry и generated artifacts в WMS-201 не изменены.
Это документирование будущих границ, не заявление о готовом fulfillment.
