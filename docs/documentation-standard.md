# Стандарт документации

Обязательные правила документации для разработчиков, менеджеров и агентов.
Документация обновляется в том же изменении, что и код, и входит в готовность задачи.

## Для кого пишем

Менеджер начинает с [продукта](product.md), roadmap и бизнес-раздела README модуля.
Разработчик читает архитектуру, технический раздел README, контракты и комментарии.
Оператор использует operations и runbooks. Агент читает AGENTS.md и эти же документы.

## Ясный технический язык: принципы ASD-STE100

Для документации и описания бизнес-процессов применять принципы
[ASD-STE100](https://www.asd-ste100.org/assets/files/ASD-STE100_ISSUE9.pdf):
простые слова, однозначные термины и ясную структуру предложений.
Стандарт описывает управляемый английский язык и содержит словарь
([официальное описание](https://www.asd-ste100.org/STE_faq.html)).
В проекте эти принципы адаптированы к русскому языку. Русские документы
не объявляются формально соответствующими английскому словарю STE.

Обязательные правила проекта:

1. Писать короткие предложения. Одно предложение передаёт одну основную мысль.
   Не убирать необходимые условия, чтобы сократить текст.
2. Использовать один термин для одного понятия. Брать определения из
   [бизнес-правил](domain.md) и контрактов. Новый термин или сокращение объяснять
   при первом использовании. Не заменять термин синонимом ради разнообразия.
3. Явно называть участника и действие: «Сервис проверяет резерв».
   Избегать оборотов «производится проверка» и местоимений с неясным объектом.
4. В инструкциях давать одно основное действие на шаг. Писать шаги в порядке
   выполнения. Сначала указывать условие, затем действие при этом условии.
5. В бизнес-процессе указывать триггер, участника, предусловия, действие,
   изменение состояния и результат. Отдельно описывать отказ, повтор и восстановление.
   Числа сопровождать единицами и границами, если они влияют на выполнение.
6. Различать обязательное правило («должен»), запрет («нельзя»), разрешение
   («можно») и предложение. Не выдавать будущую возможность за готовую функцию.
7. Убирать метафоры, канцелярит и неопределённые слова вроде «соответствующий»
   без названного объекта. Сложные условия оформлять списком или таблицей.
8. Сохранять точные имена API, полей, методов и кодов ошибок. Объяснять их смысл
   по-русски. Текст, подписи Mermaid и комментарии должны использовать те же термины.

Пример редакции текста, а не нового поведения системы:

- Неясно: «После обработки производится изменение соответствующих остатков».
- Ясно: «Сервис inventory уменьшает остаток в исходной ячейке. В той же транзакции
  сервис увеличивает остаток в целевой ячейке. При ошибке транзакция откатывает оба изменения».

Эти правила входят в ручное код-ревью. Prettier не проверяет смысл текста.

## Подход к структуре

По умолчанию controller → service → repository; README описывает публичные сервисы,
внутренние repositories и HTTP-контроллеры по необходимости. Выделение domain/ports
документируется как обоснованное отклонение, а не обязательная структура модуля.

Сервисы находятся в services/, репозитории в repositories/, DTO в dto/ внутри
модуля, даже если каждого вида пока по одному. Пустые каталоги заранее не нужны.
DTO может быть внутренним interface либо HTTP class; его назначение и место
runtime-валидации явно документируются. Наличие TS interface не означает проверки ввода.

## Каждый модуль

У каждого backend-модуля, включая shared и infrastructure при их создании,
обязателен README по [шаблону](templates/module.md): назначение, роли, сценарии,
критерии приёмки, ответственность, данные, API, события, ошибки, транзакции,
конфигурация, файлы, проверки, эксплуатация, ограничения и статус реализации.
Неприменимые разделы объясняются, запланированное явно помечается.
До реализации бизнес-модулей их описание находится в architecture и product.

### Взаимодействие и движение данных

В README модуля обязательны:

1. Mermaid sequence/flowchart с реальными точками входа, сервисами, repositories,
   БД и transport/consumer, если они существуют. Связи подписать операциями/данными.
2. Пошаговый сценарий: источник input, DTO, проверка доступа, validation,
   преобразование данных, SQL/событие, результат и получатель результата.
3. Владелец транзакции и момент commit/rollback; нельзя путать выполненный INSERT
   с уже подтверждённой операцией. Для read-only указать отсутствие записи.
4. Синтетический пример входа и результата, включая изменённые/отфильтрованные поля.
5. Ошибки по шагам и поведение повтора, ссылки на сценарии тестов и общий runbook.

Менеджеру должно быть понятно, что произошло с операцией при сбое; разработчику —
какие данные и ответственность передаются на каждом вызове. Схема Nest DI сама
по себе не заменяет описание исполнения. Будущие endpoints/consumers не показывать
как работающие; если модуль только внутренний, входом будет вызывающий сервис.

### Подробный флоу сценария

При добавлении или изменении сценария описывать его исполнение подробно, включая
графическое представление Mermaid. Это часть готовности задачи, не отдельный будущий
этап документации. Перечня классов, общей схемы DI и одной стрелки «service → БД» недостаточно.

README модуля содержит обзор и ссылки. Для сложного сквозного сценария подробный
разбор можно вынести в `docs/flows/<scenario>.md`, включив файл в карту и каталог.
Не копировать один большой флоу в несколько README: подробности имеют одного владельца.
Пример реализованного формата — [worker flow](flows/worker.md).

Описание должно позволять проследить конкретные данные от входа до результата:

1. Триггер, участники, предусловия и фактический статус: production, test-only или план.
2. Входной DTO/message/context: источник каждого существенного поля, доверие и нормализация.
3. Пошаговые вызовы реальных методов: проверки, преобразования, SQL/события и результат шага.
4. Границы процессов и транзакций, владелец commit/rollback, locks и область их действия.
5. Ветвления: validation/authorization failure, повтор/дубликат, конфликт, timeout и сбой.
6. Изменение состояния до/после commit; что видит другой запрос/worker в промежутке.
7. Для конкурентного/фонового сценария — порядок, lease/token/cursor, retry/dead/recovery
   и graceful shutdown, если эти механизмы существуют в реализации.
8. Сквозной синтетический пример с промежуточными данными и проверяемым итогом;
   ссылка на тест или иной evidence каждой существенной ветки.

Графика дополняет пошаговый текст. Для сложного сценария разделять представления:

- Обзорный flowchart: участники, начало/конец и основные ветви для менеджера.
- Sequence diagram: вызовы, перенос DTO/context, SQL и commit/rollback для разработчика.
- State diagram/отдельные flowcharts: состояния, ошибки, конкуренция и восстановление,
  когда они существенны. Простой read-only сценарий не требует искусственной state machine.

Подписывать стрелки данными или действиями; явно обозначать условия и последствия
ветвей, включая отсутствие эффекта. На сложной схеме лучше несколько читаемых диаграмм
по фазам, чем один граф со всеми деталями. Реализованное и будущее отделять подписями
и текстом: например, тестовый handler не выдавать за работающий бизнес-consumer.
При изменении кода одновременно обновлять шаги, диаграммы, пример и ссылки на проверки.

## Каждый файл

- Исходники, скрипты и тесты: file-level TSDoc/JSDoc или комментарий языка
  с назначением, местом в системе и существенными эффектами/ограничениями.
- Публичные классы и функции: контракт, неочевидные параметры, результат,
  ошибки, I/O, транзакционные требования и гарантии повторного вызова.
- Тесты: проверяемый инвариант, сценарий сбоя и нужное окружение.
- JSON и другие конфигурации без комментариев: назначение и значимые настройки
  в ближайшем README и [каталоге файлов](file-catalog.md). Не добавлять комментарии в JSON.
- Миграции: смысл изменения, constraints, совместимость и влияние на данные.
  Применённые миграции не редактируются ради комментариев.
- Документы: введение с назначением. Assets: происхождение и использование.
- Lockfile и generated code: генератор, команда регенерации, запрет ручного редактирования.
- Каждый собственный файл включается в каталог. Исключены зависимости, build output,
  IDE/cache, секреты и внутренние файлы Git.

Писать содержательно: назначение, причины и гарантии вместо комментария каждой строки.
Не дублировать TypeScript-типы в словах без объяснения смысла.
Общие правила описываются один раз: domain — инварианты, outbox — доставка,
contracts — форматы; README модулей ссылаются на них.

### JSDoc и комментарии к выполнению

Поясняющие комментарии и JSDoc/TSDoc пишутся на русском, включая CLI, Dockerfile,
Compose и тесты. Идентификаторы, флаги, имена полей и машинные коды остаются на английском.
Применённые SQL и generated output ради перевода не редактируются: пояснения дополняются
у владельца схемы/генератора и в ближайшем README.

Для нового и изменяемого кода обязательны не только file-level docs и README,
но и JSDoc/TSDoc контрактов, а также комментарии к нетривиальной реализации.
Указывать источник/доверие параметров, результат, ошибки, I/O, повторный вызов,
владельца транзакции и момент commit/rollback. @param/@returns/@throws использовать,
когда они добавляют смысл сверх TypeScript-типа. Объяснять причины проверок,
преобразование DTO/snapshot, ожидание блокировок и выбор ветки replay/conflict.
Test support документирует fault injection, barriers/timeouts и ожидаемые инварианты.
Не комментировать каждую очевидную строку; общие правила связывать ссылками с контрактом.
Generated artifacts получают описания из схемы/генератора, output вручную не правится.

### Пояснения schema-файлов

У каждой колонки в собственном schema-файле описывать предметный смысл и причину выбора
типа, default/nullable и существенные ограничения. Для UUID различать идентичность и FK,
для чисел — SQL/JS/JSON диапазон и единицы, для времени — бизнес-время/вставку/lease,
для JSONB — структуру/валидацию и отличие от исходных bytes. Объяснять составные ключи,
CHECK и назначение индекса рядом с ними; не выдавать TypeScript $type за проверку БД.
Общие особенности типов описаны в [справочнике](database-types.md); локальное назначение
поля остаётся в коде. Applied SQL и generated output ради таких пояснений не менять.

## Готовность изменения

1. Обновлены README модуля, file-level docs и file catalog.
2. Изменение поведения отражено в контрактах и бизнес-документации.
3. Описаны ошибки, конфигурация, миграции, примеры и проверки.
4. Команды существуют, ссылки рабочие, план отделён от реализации.
5. Проверено повторное использование по shared.md.

Пока это требования review. Автоматические CI gates полноты документации,
TSDoc и ссылок ещё не реализованы.

## Форматирование

Prettier закреплён root devDependency. Из корня `pnpm format`, затем `pnpm format:check`.
Настройки находятся в .prettierrc.cjs; .prettierignore защищает applied SQL/migrations,
generated code/OpenAPI, lockfile, credentials и build outputs. Не снимать эти исключения
ради зелёного formatter check: generated меняется через его generator, SQL — новой миграцией.
Форматирование не подтверждает бизнес-инварианты и не заменяет build/typecheck/Jest.

## Проверка документации при code review

Следовать [стандарту review](code-review.md). Проверять не только новый раздел, но и прежние
утверждения README, комментарии, карту docs и статусы. Историческое «не реализовано» должно
быть датировано либо заменено актуальным статусом; дописанный в конце новый статус не устраняет
противоречие в начале. Evidence указывает реальные команды/тесты и границы измерения coverage.
